## 3. Причина шума в покое (главный вывод аудита)

Кривая шасси, применённая 16.11 (правка D3): `40→45, 50→55, 60→65, 70→78, 75→85, 80→95, 90→100`.
Её нижняя половина поднята сразу на 45 %, и она смотрит на **максимум** трёх температур. В покое GPU 43–44 °C,
то есть ведущим становится **CPU**: по замеру REZ_11 в покое `Core (Tctl/Tdie) = 62,6 °C`.

Расчёт по калибровке Fan #4 (100 % = 1165 об/мин), `quiet_calc.py`:

| T макс | было до 16.11 (кривая только по CPU) | сейчас (D3) | воет? |
|---|---|---|---|
| 50 °C | 40 % → 517 об/мин | 55 % → 692 | +34 % |
| 60 °C | 50 % → 630 | 65 % → 808 | +28 % |
| **62,6 °C (покой)** | **54 % → 681** | **68 % → 844** | **+24 % оборотов ≈ +5 дБ, и это сразу 4 вентилятора** |
| 78 °C (генерация) | 83 % → 991 | 91 % → 1072 | +8 % |

Именно это и слышно постоянно: правка D (полезная под нагрузкой) в покое подняла шасси на четверть,
и этот побочный эффект в REZ_11 (раздел 9) был отмечен, но решение тогда принято не было.
A/B-тест «низкие обороты vs кривая» 16.11 08:07 (вариант `low` = плато 40 % до 90 °C) вердикта не получил;
живой конфиг после него — именно кривая D3, а не `low`.

Второй источник шума, независимый от GPU: **Fan #6 «Южный мост»** — малый 40 мм вентилятор, кривая
`40→40, 55→60, 70→80, 85→100` при калибровке 40 % = 2463, 50 % = 3046, 60 % = 3558 об/мин.
В покое чипсет 45–50 °C → 2500–3200 об/мин: это самый слышимый источник в корпусе, и он не зависит от
нагрузки на карты вообще.

Третье: кривые GPU выходят на 100 % (4466 об/мин) уже при 78 °C — под генерацией карта воет на максимуме.
Для «тихого» режима это много; тепловых запас это позволяет снять (см. п. 4).

## 4. Предлагаемая конфигурация «тихо» (отдельный файл, не трогая base_conf1.json)

Принцип: **не откатывать правку D** (защита по самому горячему источнику остаётся), а перестроить нижнюю
половину кривых так, чтобы покой стал тише прежнего, а выход на максимум начался позже — там, где он реально
нужен. Активным делается новый файл `quiet_conf1.json`; `base_conf1.json` ( нынешний, «производительный»)
остаётся нетронутым и переключается в UI FanControl в один клик.

**Шасси (тот же датчик max GPU+CPU):** `40→35, 50→40, 58→45, 65→52, 70→62, 75→75, 80→88, 85→100`

| T макс | сейчас | тихо | эффект |
|---|---|---|---|
| 45 °C | 631 об/мин | 480 | −24 % |
| 62,6 °C (покой) | 844 | **626** | −26 % к теперешнему, −8 % к до-D3 |
| 70 °C | 947 | 775 | −18 % |
| 78 °C (генерация) | 1072 | 994 | −7 % |
| 85 °C и выше | 1139 | **1165 (100 %)** | защита полнее: 100 % наступает при 85, а не при 90 °C |

**GPU (обе карты, один профиль):** `30→25, 40→30, 50→38, 60→48, 66→56, 72→64, 78→75, 82→88, 86→100`

| T gpu | сейчас | тихо |
|---|---|---|
| 44 °C (покой) | 1761 | 1549 |
| 70 °C | 3694 | 2730 |
| 78 °C (генерация) | **4466 (100 %)** | 3364 (75 %) |
| 86 °C | 4466 | 4466 (100 %) |

Запас по теплу: по NVML (REZ_09, п. 4) при 78 °C запас до теплового лимита ~10 °C, при 82 °C ~6 °C,
при 86 °C ~2 °C — то есть 100 % в тихом профиле включается ровно перед порогом троттла, а не за ним.
Цена: в тихом режиме длинные генерации будут на ~4–6 °C горячее и на несколько % медленнее.

**Южный мост:** `40→30, 50→35, 60→50, 70→65, 80→85, 90→100` (в покое 2100–2600 вместо 2500–3200 об/мин,
полный поток при 90 °C).

**CPU (Fan #2) — не трогаем.** Он не заявлен как источник шума, и запас по процессору лишний раз не нужен.

Гистерезис во всех новых кривых — как в работающих: вверх 3 с / вниз 12 с, ±2 °C (у GPU вверх 2 / вниз 7).

## 8.2 Корень проблемы (26.11.2026 01:30): FanControl живёт своим `userConfig.json`

Обратная связь после второго шага: «ещё гудит». Канал IPC (см. ниже) показал, что температуры и обороты живые,
но ШИМ контроллеров шасси/CPU/чипсета стоит намертво: Fan #6 = 56,5 % при чипсете 54,5 °C, Fan #2 = 71,4 %
при Core 61 °C, Fan #4 = 64,3 %. Это значения от горячего всплеска ~30-летней давности по времени, а не от кривой.

Причина: **FanControl при запуске восстанавливает своё живое состояние из `Configurations\userConfig.json`,
а не именованный профиль из `CACHE`.** В `userConfig.json` (записан 01:21:01, 16 122 байта) сидели:

* старая кривая `Graph Chipset` = `39.77→40.06, 54.65→60.06, 69.88→79.52, 84.9→100` (моя правка в файл — не в приложение);
* **нет** кривой шасси и **нет** составного датчика `Mix/Максимум GPU+CPU` (`CustomSensors` пуст);
* Fan #4 «Шасси» привязан к кривой `Graph`, то есть к датчику GPU, а не к максимуму GPU+CPU.

Плюс `CACHE.CurrentConfigFileName` слетел на `FanControl.Service.deps.json` (мусорный `*.json` из той же папки).
Вывод: **подкладывание файла + перезапуск процесса — механизм неприменимый**; обе правки 8.0 и 8.1 до этого
момента работали только «на бумаге».

Рабочий механизм — **команда `LoadConfig` живому процессу** через тот же именованный канал
(`FanControlRPC.LoadConfig(Path)`, ответ `Ok`). После неё цикл управления оживает за десятки секунд:

| параметр | до LoadConfig | +90 с |
|---|---|---|
| Fan #6 «Южный мост» | 56,5 % → 3488 об/мин | 45 % → 2761 об/мин (продолжает снижаться) |
| Fan #4 «Шасси» | 64,3 % → 802 | 58 % → 733 |
| Fan #2 «CPU» | 71,4 % → 1968 | 56…68 % → 1746 |
| `CACHE.CurrentConfigFileName` | `FanControl.Service.deps.json` | `quiet_conf1.json` |

Побочный результат: тот же канал даёт полный доступ к чипу без прав администратора — `SensorsRPC.GetAllSensors`
(105 сенсоров) и `ReadSensorValues` (105 значений), включая `Core (Tctl/Tdie)`, температуры NCT6796D,
обороты всех вееров и ШИМ. Скрипты: `ipc_sensors_probe.ps1`, `ipc_watch.ps1` (CSV), `ipc_state.ps1`,
`ipc_load.ps1`, `apply_night.ps1`.

### 13.5 Интерпретация и что проверять дальше

Наблюдение «0 % и 0 об/мин во всех режимах, включая холодный старт и 180 Вт нагрузки, при
идентичном с рабочей картой vBIOS» объясняется двумя версиями:

* **А. Механическая/электрическая неисправность кулера** (обрыв, неотжатый коннектор на плате карты,
  заклинившая крыльчатка, умерший драйвер веера на самой карте). Наиболее вероятна.
* **Б. Неисправность таходатчика при живом веере** — но пользователь видит, что крыльчатка
  не вращается, поэтому версия Б сама по себе не объясняет отсутствие вращения.

Порядок проверки, который я рекомендую (по возрастанию трудоёмкости):

1. **Холодный старт:** при включении питания большинство карт на 1–2 с прокручивают все веера.

2. **Осмотр на обесточенной машине:** покрутить крыльчатку пальцем (должна идти мягко, с лёгким

   на плате карты; проверить, нет ли кабельной стяжки или препятствия.
3. **Независимый софт:** MSI Afterburner (на машине установлен, `C:\Program Files (x86)\MSI Afterburner`,
   рядом RTSS) — включить пользовательскую кривую веера только для этой карты и поставить 100 %.
   Это другой путь NVAPI, чем FanControl. Если и там веер не оживает —software-версии исчерпаны.
4. **Кросс-проверка стендом:** переставить карту в другой слот / в другой ПК. Если и там 0 RPM
   при 180 Вт — карта подлежит гарантии/ремонту.
5. **Временные меры, если работать надо сейчас:** ограничить мощность

   температуры снизится на несколько градусов), держать боковую стенку открытой или направить
   поток корпусного веера прямо на карту, в рабочих профилях держать шасси включённым.

## 15. Развязка: веера исправны, причиной была упаковочная плёнка (26.11, 21:44-21:55)

### 15.1 Что обнаружил пользователь

При осмотре с фонариком оба кулера вращаются, карты новые. У **нижней** карты (слот x4) под
вентилятор подмяло упаковочную полиэтиленовую плёнку; плёнку сняли полностью с обеих карт.
Веера не крутятся только при отсутствии нагрузки — и HWiNFO это показывает.

Это объясняет наблюдение раздела 13 без обращения к неисправности: плёнка мешала крыльчатке
вращаться (и дополнительно мешала притоку воздуха), поэтому при 180 Вт верхняя карта стояла

### 15.3 Исправление моих ошибок в интерпретации

1. **«0 об/мин в простое = дефект»** - неверно. У обеих карт штатный режим 0 dB: до 53 C
   веера обесточены, это норма. Дефектом было то, что веер не начинал вращаться и при 87 C.
2. **Косвенное рассуждение «одинаковые плато 84 и 83 C доказывают, что оба кулера работают»**
   - неверно, и я это утвержал вслух. Радиатор этой карты рассчитан на больший пакет, чем
   180 Вт, поэтому без вращения она греется лишь на 1-3 C сильнее. Разница в 6-9 C проявилась
   только после удаления плёнки (87 -> 79 C в изолированном прогоне).
3. Вывод раздела 13.5 («наиболее вероятна механическая неисправность кулера») оказался верен
   по классу (механическое препятствие), но неверен по диагнозу «неисправность»: препятствие
   было внешним и устранимым.

### 15.4 Что это меняет для эксплуатации

* Верхняя карта теперь охлаждается **лучше нижней при вдвое меньшей скорости кулера**
  (78 C на 2950 об/мин против 82 C на 4300 об/мин): теплопакет в корпусе стал мягче,
  и 40 мм веер чипсета под нагрузкой перестал запускаться.
* Под долгими генерациями теперь будут слышны оба кулера карт (у нижней до 95-98 %) -
  это штатное поведение, а не шум настройки. В простое по-прежнему тишина.
* Стоит убедиться, что внутри кожуха верхней карты не осталось обрывков плёнки (именно там
  крыльчатка упиралась), и при случае повторить осмотр после первой же долгой генерации:
  температура 03:00.0 должна оставаться в районе 77-80 C при 180 Вт.
* Из открытого измерения остаётся HOT SPOT: его стоит снять в HWiNFO при 180+180 Вт,
  чтобы знать реальный запас до троттлинга (раздел 13.6).

### 16.1 Интерпретация

1. **Запас до троттлинга надо считать по горячей точке, а не по ядру.** По ядру казалось
   85,8 против порога ~95 C (10 C запаса), по горячей точке нижняя карта уже доходила до 98,3 C
   при ориентировочном пределе около 110 C - то есть запас около 12 C, а не 25.
2. **Нижняя карта в слоте x4 - самая горячая и самая шумная**: 82,4 C ядром и 80 % кулера против
   76,3 C и 63 % у верхней при той же мощности. Виноват не лимит мощности (он одинаковый),
   а обдув: верхняя карта стоит в x16 и получает поток, нижняя зажата снизу и греется
   от карты над ней.
3. **Память ГП 75-77 C при максимумах 82,5-85 C** - для GDDR7 это комфортно (предел
   ~95-100 C), память не лимитирует.
4. **Линк PCIe 16,0 GT/s у обеих карт** - это поколение 3.0, хотя плата X570 даёт 4.0, а карты
   по паспорту 5.0 (минимум 2,5 GT/s по колонке - просто простой в ожидании). Ширину линии
   HWiNFO в этой строке не показывает; по словам пользователя нижняя карта сидит на x4, тогда
   её пропускная способность порядка 3,5 ГБ/с против порядка 14 ГБ/с у верхней. Для загрузки
   16-ГБ модели это несколько секунд вместо пары секунд - заметно при смене модели, но на
   скорость самой генерации при полностью загруженной в видеопамять модели не влияет.
   (Первоначально я оценил это как «сотни МБ/с» - неверно, это единицы ГБ/с.)
5. Все ограничители частот в кадре показывают ~100 % (нет снижения), что согласуется
   с нулевыми флагами троттлинга из  nvidia-smi (разделы 11, 13.2).

### 16.2 Оговорки по данным

Значения сняты с одного скриншота, поэтому это один снимок в один момент, а не ряд: минимумы и
максимумы накоплены HWiNFO с момента запуска (не за конкретный прогон), а по некоторым
строкам накопленные «среднее/максимум» внутренне несогласованы (например, по памяти ГП
среднее больше максимума), что типично для смешения интервалов выборки. Для коллеги
важны именно текущие значения и максимумы горячей точки. Если нужен машиночитаемый
лог - в HWiNFO есть экспорт CSV: прогон 10 минут при 180+180 Вт с записью
GPU Hot Spot Temperature, GPU Temperature, GPU Core Current и GPU Fan.

Практический вывод для долгой генерации: если обе карты держать на 180 Вт, лимитирующим
элементом становится горячая точка нижней карты. Варианты, по возрастанию вмешательства:
понизить лимит нижней карты до 150-160 Вт ( nvidia-smi -i 1 -pl 150), поменять карты местами
(верхняя охлаждается лучше), либо направить на нижнюю карту поток корпусного веера.
