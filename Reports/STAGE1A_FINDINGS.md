## 2. Готовый HTML-экспорт ACE: что он реально содержит

Вопрос поставлен так: можно ли считать HTML-экспорт источником данных для StrawBerry Edition. Ответ ниже — по замерам, а не по коду.

### 2.1 Как устроен конвейер HTML-экспорта (код)

Для формата `html` (и `doc`) в `entrypoints\content.js:606-638` выполняется последовательно:

1. разбор чата (`parse({full:true, includeImages:true})`) — для ChatGPT картинки приходят data URI из `backend-api` (`content\chatgpt_helper.js:172-198`: `files/download/<id>` → `download_url` → blob → `FileReader.readAsDataURL`);
2. `inlineConversationImages()` (`content\utils\image-inliner.js:168-180`) — **только для `doc` и `html`**: берёт все внешние и `blob:` ссылки картинок из текста и подменяет их base64; скачивание идёт с `credentials:'include'` и таймаутом **4 секунды** на ссылку (`image-inliner.js:41`), при неудаче ссылка остаётся как есть;
3. `applyAttachmentOption()` (`content\utils\strip-attachments.js:383-393`) — только правки текста;
4. `HtmlFormatter.format()` (`content\formatters\html.js`), затем DOMPurify (`content\utils\sanitizer.js:34-38`).

Изображения вставляются тегом `<img src="…">` (`html.js:1286-1309`) с CSS `max-width: 350px`. Ограничение по ширине — только отображение, байты не меняются: ни canvas, ни `toDataURL`, ни пересжатия в HTML-форматтере нет (поиск по `toDataURL|canvas|resize|quality` в `content\` даёт попадания только в `formatters\image.js`, то есть в PNG-скриншот страницы, и в библиотеки).

### 2.2 Реальный прогон на файлах из архива StrawBerry

Оригиналы брались из `G:\Strawberry\attachments\<имя_чата>\<sha256>.<расш.>` — имя файла в хранилище StrawBerry и есть SHA256 байтов, что сразу даёт эталон для сверки. Из них собран объект разбора ровно той же формы, которую выдаёт ChatGPT-парсер ACE, и прогнан через шаги 2–4 выше.

| Оригинал | Размер | SHA256 | Что получилось в HTML | Совпадение байтов |
|---|---|---|---|---|
| JPG 945 770 б | 945 770 | `6bf9354b…8b9368` | `<img src="data:image/jpeg;base64,…">`, декодировано 945 770 б | SHA256 **полностью совпал** |
| WEBP 535 604 б | 535 604 | `10712152…de00d` | data URI, 535 604 б | SHA256 **полностью совпал** |
| JPG 733 290 б | 733 290 | `8b4f5fa7…10fae` | data URI, 733 290 б | SHA256 **полностью совпал** |

То есть сам форматтер не трогает байты: то, что попало в data URI, выходит из HTML байт в байт (размер и SHA256 совпадают). DOMPurify (тот же код `purify.es.js`, что и в браузере, с теми же опциями) на HTML объёмом 3 421 527 байта: 7 тегов `<img>` до и 7 после, 5 data URI после, все data URI идентичны исходным, время 3 мс — больших data URI санитайзер не режет и не выбрасывает.

Масштаб (тот же конвейер, картинки дублируются):

| Картинок | Байт картинок | Размер HTML | Время форматирования | RSS процесса |
|---|---|---|---|---|
| 12 | ~2,2 МБ | 11 848 709 б | 223 мс | 183 МБ |
| 60 | ~11 МБ | 59 138 069 б | 1 112 мс | 468 МБ |

Все 60 картинок в HTML остались с идентичными SHA256. Наценка base64 ≈ +33 % к байтам файлов; один HTML-файл на весь чат, вложений как отдельных файлов в нём нет.

### 2.3 Ключевое ограничение: картинка в HTML ≠ оригинал файла

Эксперимент с двумя рендициями одной фотографии на CDN:

| Ссылка | Байт в data URI | SHA256 |
|---|---|---|
| `…unsplash…?w=400` | 28 359 | `a5da8868…e1974c` |
| `…unsplash…?w=1600` | 298 542 | `f3a4e480…3c59eb` |

Одна и та же фотография даёт разные байты и разные SHA256 в зависимости от того, какой URL попал в текст чата. ACE честно кладёт в HTML **то, что отдал URL**, и отличить уменьшенный рендиш от оригинала по содержимому HTML нельзя. Поэтому наличие картинки в HTML не является доказательством сохранения оригинального файла — доказательством может быть только SHA256, сверенный с эталоном из источника (`files/download` или официального пакета экспорта).

Что происходит со ссылками, которые не удалось скачать:

| Случай | Поведение (замерено) |
|---|---|
| Ссылка отдаёт 404 | `fetchUrlAsDataUri` вернул `null` за 534 мс; в HTML осталась внешняя `<img src="https://chatgpt.com/backend-api/files/download/…">` — файл не сохранён, HTML не самодостаточен |
| Ссылка на PDF в позиции картинки | в HTML остался `<img src="…/backend-api/files/download/<file_id>">`; это не сохранённый файл, и вне авторизованной сессии ChatGPT такой адрес не отрисуется |
| Ссылка живая | подменяется base64 (замеры 548 мс и 738 мс на 28 КБ и 299 КБ) |

### 2.4 Документы и другие вложения в HTML

| Проверка | Результат |
|---|---|
| Байты PY (10 218 б) в HTML | нет (искался base64 первых 64 байт — не найден) |
| Байты JSON (29 673 б) в HTML | нет (искался заголовок файла как текст — не найден) |

| Что делает опция «файлы выключены» | из текста вычёркивается содержимое вложений, остаются только имена; при «картинки выключены» (`stripImages`) байты картинок исчезают совсем |

### 2.5 Имена файлов и связь «картинка ↔ файл»

- У всех `<img>` в HTML атрибут `alt="Image"` — имён оригинальных файлов у картинок нет (замерено: 7 тегов, 7 раз `Image`).
- Имена файлов в HTML встречаются **только** в строке `[Attached: …]`, это простой текст через запятую, без идентификаторов, размеров и MIME.
- Идентификаторов ассетов (`file_…`, `cdn://…`) в HTML нет.
- Структура сообщений в HTML машинно-читабельная: `<div id="msg-card-N" class="message-card role-user|role-assistant">`, то есть порядок сообщений и роли восстанавлимы; `message_id`/`parent_id` и дата с точностью до секунд — нет (даты выводятся в локализованном виде `23.10.2026 04:31`, без секунд и часового пояса).

### 2.6 Вывод по использованию HTML-экспорта как источника данных

| Возможность | Оценка |
|---|---|
| HTML как основной источник вложений | **нет**: ни байтов документов, ни имён картинок, ни идентификаторов ассетов, ни точных дат |
| HTML как аварийный канал для картинок | **да, с оговоркой**: если в тексте чата уже стоит data URI, то в HTML попадает копия байт в байт (подтверждено SHA256). Подходит для восстановления уже потерянных картинок, но требует сверки SHA256 с эталоном, иначе нельзя отличить рендиш от оригинала |
| HTML как источник для обычных чатов и публичных ссылок | для публичных `/share/` картинок — только если ACE сумел скачать их по URL (ограничение 4 с на ссылку), иначе в HTML останутся внешние ссылки |
| Риск молчаливой потери | есть: недоступная ссылка не приводит к ошибке экспорта, в HTML просто остаётся внешний URL |

Практический вывод для архитектуры (без её изменения): основным источником байтов остаётся путь «идентификатор ассета → `backend-api/files/download` → файл в `attachments\`», а HTML-экспорт — только вспомогательный канал для изображений с обязательной SHA256-сверкой.

## 5. Подтверждено и не подтверждено

Подтверждено экспериментально на этом шаге:

1. Форк собирается на установленном Node 24.16 без переносного Node 26; сборка пригодна к загрузке как unpacked и реально запускается.
2. Id unpacked-расширений не конфликтуют (нет `key` в манифесте → id из пути), но одинаковые `commands` и одинаковое имя приводят к отключению копий; Firefox требует другого gecko id; помощник страницы перехватывает чужие сообщения из-за общего `source`, общего флага и общего id скрипта.
3. В HTML-экспорте картинки хранятся base64-data URI и не преобразуются: SHA256 и размер совпадают с оригиналами из архива StrawBerry; DOMPurify их не трогает; масштаб до 60 картинок (59 МБ HTML, 1,1 с) потерь не даёт.
4. HTML не хранит: байты документов, имена картинок, идентификаторы ассетов, точные даты, `message_id`/`parent_id`. Недоступные ссылки остаются внешними.
5. Картинка, полученная по внешнему URL, может быть рендишем: две рендиции одной фотографии различаются и размером, и SHA256.
6. `backend-api/conversation`, `backend-api/files/download` требуют авторизации; маршрута `files/<id>/metadata` не существует.

Не подтверждено (решается прогоном зонда с авторизованной сессией):

1. Жив ли `files/download/<id>` сейчас для PDF/PY/JSON/DOCX/XLSX и для «старых» чатов (сентябрь–октябрь 2026) — есть 53 реальных `source_id` для проверки.
2. Возвращает ли `files/download` оригинальные байты загруженного пользователем файла (сверка с SHA256 из архива — сравнение будет автоматическим) и что он возвращает для **сгенерированных** ChatGPT изображений.
3. Есть ли `id` в `metadata.attachments[]` в текущем формате ответа и в какой форме приходят идентификаторы сгенерированных картинок.
4. Работают ли те же адреса на публичных `/share/`-ссылках и на страницах, открытых без токена.
5. Срок жизни подписанных `download_url`, лимиты на размер файла и на количество обращений.
6. Фактический предел postMessage/памяти/JSZip для больших чатов в браузере (наши лимиты 32 МБ на файл и 100 МБ на чат — ограничения кода, не замеры).
7. Поведение помощника форка при одновременно установленном ACE в реальном браузере (в коде конфликт виден, в живой вкладке не проверялся).

## 6. Что нужно, чтобы закрыть шаг 1а

Нужен доступ к живой сессии ChatGPT в браузере пользователя. Варианты, по убыванию удобства:

1. **Зонд в консоли** (рекомендую): открыть обычный чат ChatGPT → F12 → Console → вставить целиком `StrawberryEdition\probe\chatgpt_asset_probe.js` → Enter.
