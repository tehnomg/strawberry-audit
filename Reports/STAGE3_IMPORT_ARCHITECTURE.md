### 1.3 Как устроен v2-движок (это ядро унификации)

Поток один и общий для всех форматов (`engine.py`):

```
входы → run() (папка: rglob + фильтр расширений) → load_payload() (30–48)
      → detect_adapter() (adapters/__init__.py) → adapter.parse() → нормализованная модель (model.py)
      → graph.path_to_leaf() (60) → attachments.stage_attachments() (attachments.py:125)
      → store.decide() (store.py:135) → backup_chat (76) → atomic_write (86)
      → report.summarize()/write_json() (report.py)
```

Контракт адаптера (`adapters\base.py`): `detect(payload) -> (уверенность, источник)`,
`parse(payload, ctx) -> чат`; контекст `Context` несёт `input_path`, `attachments_dir`,
`assets_dir`, `lmstudio_files_dir`, `local_tz`, `extra` и `file_sha256()`.
Ошибки формата — `AdapterError(code, message)` (`base.py:13–18`).

Нормализованное сообщение (`model.py:23–42`): `role, text, time, time_precision, message_id,
parent_id, reasoning, tools, images, files, model, edited`.
Вложение — плоский dict (`model.py:45–79`) + служебные ключи `_payload/_data_uri/_local_path/_asset_ref`,
которые не попадают в архив (`INTERNAL_ATT_KEYS`, `model.py:120`).
В архив из сообщения попадают только `role/text/time/reasoning(+секция инструментов)/images/files/
model/message_id/parent_id/edited` (`archive_message`, `model.py:143–160`) — всё остальное
адаптер обязан уместить в эти поля, иначе теряется.

Хэши считаются по тому, что лежит в архиве (`model.py:115–117`), поэтому «источник изменился»,
«сдвинулись только даты/id» и «чат правил человек» различимы; `status`/`url` вложений из хэша
исключены (`VOLATILE_ATT_KEYS`, `model.py:119`), а `sha256/size/mime/name` — входят
(`_att_identity`, `model.py:175–185`). Следствие: если сначала импортировать чат без байтов
вложений, а потом с байтами — хэш изменится и будет `UPDATE` (проверено в `edge_report.txt`).

Действия записи: `NEW, SKIP, DATE_UPDATE, UPDATE, MIGRATE, SKIP_LOCAL, CONFLICT, ID_MISMATCH,
CORRUPT, DUP` (`store.py:122`). Локальная правка детектируется пересчётом хэшей по файлу
(`recompute_hashes`, `model.py:225`), поля `imported_at/first_imported_at/source_created_at/
pinned/archived` сохраняются при перезаписи (`merge_fields`, `store.py:187–203`).
Ветки: в архив идёт одна активная цепочка (`path_to_leaf`, `graph.py:60`), остальные узлы
только считаются (`count_branches`, `graph.py:122–127`, `nodes_outside_active`).

Действие `DUP` объявлено, но **нигде не присваивается** (поиск по пакету: только `store.py:122`) —
средства различить «два файла с одним и тем же чатом» в v2 фактически нет (см. раздел 9, дефект 7).

## 4. Формат StrawberryEdition (ZIP) в единой системе

Напоминание формата (спецификация этапа 2, `STAGE2_TECH_SPEC.md`; типы вложений разобраны
в `STAGE3_MEDIA_TYPES.md`, здесь не повторяем): один ZIP, внутри JSON диалога в формате
Strawberry v1.1, папка вложений с ASCII-именами `<attachmentId>.dat`, оригинальные имена
(в том числе кириллица) — только в `manifest.json`; в манифесте `sha256` и `size` каждого файла;
вложения складываются в две корзины `images`/`files`, `kind` = `image`/`file`, семантика типа —
в отдельном поле, `name` обязано нести настоящее расширение, `format_hint` — страховка.

Что нужно, чтобы этот формат стал входом `import2.py` без новой параллельной системы:

1. **Распаковка до импорта, а не адаптер-читатель ZIP.** `load_payload` (`engine.py:30–48`)
   не умеет бинарные входы: ZIP как явный вход даёт `UnicodeDecodeError`, битый ZIP —
   `JSONDecodeError`, и то и другое записывается в `read_errors`, а rc остаётся 0.
   Предлагаемый минимальный шаг: диспетчер (см. раздел 5) видит `.zip`, открывает его,
   определяет структуру и вызывает штатный механизм на распакованном каталоге с
   `--assets-dir` на распакованные байты. Сам `import2.py` при этом не узнаёт о ZIP ничего,
   кроме одного вызова «распакуй во временную папку и обработай как папку».
2. **Адаптер `strawberry.v1`** (уверенность 0.97 по полю `format` в JSON, алиас `--source strawberry`).
   Сейчас экспорт расширения попал бы в `browser.export-v1` с уверенностью ровно 0.9,
   который (а) не читает вложения пакета и (б) отбрасывает сообщения без текста
   (`browser_v1.py:106–107`). Поэтому отдельный адаптер нужен; правила нормализатора
   (две корзины, `name` с расширением, `format_hint`, `sha256`/`size` из манифеста) —
   из прошлого этапа, они не меняются.
3. **Временная рабочая область** — unique-каталог в `%TEMP%`, удаляется по завершении;
   содержимое ZIP не должно попадать в `chats\` и `attachments\` напрямую (требование
   этапа 2: «после импорта ZIP больше не должен требоваться», структура хранения не меняется).
4. **Контроль целостности** — перед записью сверить `sha256`/`size` из `manifest.json`
   с фактическими файлами из ZIP; расхождение = не «missing-вложение», а ошибка пакета
   (сейчас подобных проверок нет ни в одной из систем).

Оба требования пользователя при этом выполняются: `import2.py` сам принимает ZIP и разбирает
его, результат лежит в штатном хранилище с штатными именами, `url`, `status:"available"`
и дедупликацией; параллельного хранилища не появляется.

## 5. Проект диспетчера входов

Статус: предложение. Задача — не переписать импортёр, а добавить один слой перед ним.

### 5.1 Что диспетчер принимает

один файл; несколько файлов; папка (в том числе с подпапками); ZIP. Всё — через один вход
(CLI-аргументы `import2.py <входы...>` уже такие; UI сегодня умеет только несколько файлов).

### 5.2 Классификация: структура важнее расширения

Порядок, предлагаемый как минимально достаточный:

1. **По сигнатуре первых байтов**: `PK\x03\x04` → ZIP-контейнер (в том числе файл с «не тем»
   расширением); `%PDF`, `ID3`, `ftyp`, `RIFF…WAVE`, `GIF8`, `\x89PNG`, `\xff\xd8\xff`,
   `WEBP` → бинарный не-чат (не пытаемся читать как текст); иначе — пробовать как текст.
   Снайф байтов уже реализован для вложений (`attachments.sniff_signature`) и работает.
2. **По структуре JSON**: набор ключей (`mapping`, `messages`, `versions`, `type=="session"`,
   `format=="strawberry.v1"`) — то, что уже делают `detect()` адаптеров.
3. **По содержимому текста**: маркеры диалога для Markdown-дампов (адаптер `markdown`).
4. **По внутреннему содержимому ZIP**: наличие `manifest.json` с `format`, `conversations.json`
   + `assets/` (официальный ChatGPT), `*.conversation.json` (LM Studio); если ничего не подошло —
   классифицировать каждый вложенный файл по правилам 1–3.

Расширение используется только как подсказка для способа чтения — как и сейчас в v2.

### 5.3 «Не импортировать молча» и «не объявлять неизвестный JSON чатом»

Сегодня: файл с уверенностью ниже `--min-confidence` (0.4) получает действие `undetected`
с текстом «формат не распознан (уверенность 0.00)» — это хорошо; но файлы с неподдерживаемым
расширением в папке исчезают бесследно, а ошибочные форматы обрывают прогон (раздел 9).
Предлагается правило: **каждый принятый файл обязан попасть в одну из трёх строк отчёта —
«будет импортировано», «пропущено с причиной», «не распознано/не поддерживается»**.
Ни одна строка не появляется без причины; ни один файл не исчезает.

Порог уверенности 0.4 оставляем, но добавляем «серую зону»: если лучшее значение ∈ [0.4, 0.7)
или два адаптера различаются не более чем на 0.05 (например `browser.export-v1` 0.9 против `qwen.package`
0.8 — разные форматы одного и того же расширения), источник показывается как гипотеза и требует
подтверждения либо явного `--source`.

### 5.4 Предпросмотр до записи

Перед любой записью — таблица: файл → определённый источник → уверенность → действие
(`NEW/UPDATE/SKIP/MIGRATE/CONFLICT/…`) → число сообщений → число вложений (доступно/нет байт)
→ предупреждения. Таблица уже фактически производится (`report.summarize`, `report.py`;
`ImportStats`, `engine.py:51–82`) — не хватает только режима «показать и спросить до записи»:
в v2 для этого есть `--dry-run` (он же предупреждает о пропущенных ассетах, `engine.py:174–176`).
Предлагается: UI показывает результат dry-run, кнопка «Импортировать» выполняет тот же прогон
без `--dry-run`. Дублировать логику в браузерном JS не нужно.

### 5.5 Неоднозначности и конфликты — что предлагается

| Ситуация | Сегодня | Предлагаемое поведение |
|---|---|---|
| Два адаптера с близкой уверенностью | побеждает порядок `ADAPTERS`, пользователь не знает | показать обоих, спросить (CLI `--source`, UI — выпадающий список) |
| Уверенность < порога | строка `undetected` | «не чат» + отдельная группа в отчёте; не писать ничего |
| Неизвестное расширение в папке | файл игнорируется совсем | строка «не поддерживается» + предложение «распознать по содержимому» |
| Один и тот же чат в нескольких файлах (копии папок `Migrated`, дубли в ZIP) | последний по сортировке выигрывает, `UPDATE`, бэкапы плодятся | сравнить хэши копии; одинаковые → `SKIP`/`DUP` (действие объявлено, но не используется), разные → показать варианты и спросить |
| Локальная правка + изменившийся источник | `CONFLICT`, перезапись только с `--force` (бэкап создаётся) | как сейчас + выбор «оставить локальный / взять новый / сохранить второй как копию» |
| Неизвестный ключ верхнего уровня (`number` в 35 файлах) | игнорируется | предупреждение в отчёте |

Проверенная цепочка конфликтов (`edge_report.txt`, секция 3): первый импорт `NEW`;
правка файла интерфейсом + повторный импорт того же входа → `SKIP_LOCAL`;
правка файла + изменение источника → `CONFLICT` (ничего не перезаписано);
тот же вход с `--force` → запись с бэкапом `chatgpt-chatD_20261121_024623_853122.json`.

### 5.6 Границы ответственности (что где живёт)

* **Адаптер источника**: только перевод своего формата в нормализованную модель + `parse_report`
  (что потеряно, какие метки времени, какая политика выбора листа). Никакой записи, имён файлов,
  хэшей.
* **Диспетчер входов**: приём файлов/папок/ZIP, распаковка, сигнатуры, классификация,
  предпросмотр, запрос выбора у пользователя, список «не поддерживается». Ничего не пишет.
* **Движок (`engine`/`store`/`attachments`/`report`)**: нормализованная модель → идемпотентность,
  `original_id`/`local_id`, хэши, дедупликация и staging вложений, бэкапы, атомарная запись, отчёт.
  Единственный владелец хранилища.
* **Сервер/UI**: выбор входов, запуск движка, показ отчёта и прогресса. Никакой импортной
  логики в браузерном JS и никакого второго механизма записи в хранилище.

Порядок добавления новых источников (из прошлой договорённости): адаптер сервиса → общий
нормализатор Strawberry → экспортный пакет (JSON + attachments + manifest + ZIP) → штатный импорт
`import2.py`. Сейчас реализуем только ChatGPT, но диспетчер и контракт адаптера не должны этому
мешать: новые источники подключаются регистрами в `adapters\__init__.py`, без правок движка.

## 6. Единое окно импорта: варианты и рекомендация

Требования пользователя: одно окно для файла/нескольких файлов/папки/ZIP; импортная логика
не переезжает в браузерный JS; не появляется второй независимый механизм импорта.

### Вариант 1 — сервер запускает `import2.py` как процесс (рекомендуется)

Прецедент в том же файле есть: `asyncio.create_subprocess_exec(...)` с `cwd=BASE_DIR` и
`PYTHONIOENCODING=utf-8`, вывод разбирается (`history-server.py:1678–1685`, `1739–1743`).

Плюсы: один движок для CLI и UI (требование «не создавать второй механизм» выполнено напрямую);
крах разбора формата не роняет сервер (проверено: падение из-за дефекта 1 — это отдельный
процесс с rc=1, данные не повреждены); прогресс читается прямо из stdout; ZIP и папки
обрабатываются без переупаковки в HTTP-запрос; отчёт читается из готового JSON (`report.write_json` →
`{"summary": {...}, "chats": [...]}`).
Минусы: нужен временный файл для загруженного из браузера входа (сегодня это `%TEMP%` +
`await f.read()` целиком в память, `history-server.py:1996–2035` — размер не ограничен);
нужен короткий разбор текстового вывода; нужен реестр запущенных прогонов и блокировки (раздел 7).

### Вариант 2 — отдельный локальный сервис импорта

Плюсы: жёсткая изоляция, независимый перезапуск. Минусы: второй процесс, его порт, конфиг,
аутентификация и CORS; дублирование конфигурации хранилища; для однопользовательской локальной
системы выигрыша нет. Реализация дороже, пользы не найдено.

### Вариант 3 — импорт прямо внутри сервера (модуль + поток)

Сервер импортирует `importer_v2` и вызывает `run()` через `asyncio.to_thread`.
Плюсы: без запуска процесса, быстрый старт, отчёт напрямую в объекте.
Минусы: ошибка формата или зависание адаптера приходится на процесс сервера
(сегодняшние прогоны падают с исключением — в серверном процессе это будет 500 или зависание);
тяжёлый импорт блокирует раздачу интерфейса; сложнее ограничить память.
Гибрид: в процессе сервера для «маленьких» входов (1–3 файла), subprocess для папок/ZIP/массовых
загрузок — но это два разных пути выполнения, то есть риск расхождения поведения; предлагаемый вариант 1
такого расхождения не даёт.

**Предложение (не утверждено): вариант 1.** Существующий адрес `POST /api/import/upload`
сохраняем как точку входа UI, но внутри он собирает команду `import2.py` и запускает её;
v1-путь (`import.py`) остаётся работающим как есть и выводится из употребления только после
того, как диспетчер накроет все его форматы (список функций v1: `import.py:328, 515, 616, 672, 820, 848`
— все они имеют аналог в v2). Для совместимости с 141 «не-v2» чатом первый унифицированный прогон
по архиву должен выполняться как `MIGRATE`-прогон с бэкапом, а не как «чистка».

Что должно появиться в UI (минимум): `<input type="file" webkitdirectory>` и `.zip` в `accept`
(сегодня `accept=".json,.jsonl,.md"`, `web\index.html:333`), таблица предпросмотра из dry-run,
прогресс по файлам (сегодня — только toast в конце, `web\app.js:1499–1544`), перечень
«не распознано/не поддерживается», выбор источника при неоднозначности.

## 7. Одновременная запись и прерывание: что показали прогоны

### 7.1 Четыре процесса на один вход

Проверено (прогон 4 параллельных `import2.py` на одном файле, `dispatcher_report.txt`, секция I;
подробный stderr — `gaps_report.txt`): **2 процесса из 4 завершились с rc=1** —

```
RuntimeError: не удалось заменить qwen-qtest-1.json: [WinError 2]
Не удаётся найти указанный файл: 'qwen-qtest-1.json.tmp' -> 'qwen-qtest-1.json'
```

Причина — `store.atomic_write` (`store.py:86–107`) использует **фиксированное** имя
`path.with_suffix(path.suffix + ".tmp")`; второй процесс забирает этот tmp-файл, и оба
«временных» файлов сталкиваются. Шестикратный повтор `os.replace` с паузой 0.15 с не спасает,
потому что победитель всегда переименовывает *чужой* tmp. Файлы чатов после этого остались
читаемыми, `.tmp` не осталось, бэкапов нет.

Минимальное исправление (не выполнялось): уникальное имя временного файла —
`tempfile.mkstemp(dir=path.parent)`, как это уже делает сервер
(`history-server.py:286–295`, `1059–1065`).

Дополнительный риск того же рода: старт сервера удаляет все `*.tmp` в `chats\`/`backup\`/
`memory\`/`profiles` (`history-server.py:88–92`) — он может стереть tmp-файл работающего
импортёра (у вложений tmp называется иначе: `<sha>.<ext>.tmp`, `attachments.py:159–260`,
и в `attachments\` стартовый клининг не действует).

### 7.2 Прерывание прогона

Проверено: прогон папки `G:\Strawberry\import` убит через 3 с (`edge_report.txt`, секция 4).
Итог: **327 записанных чатов, 0 битых JSON, 1 остаточный `.tmp`, отчёт не создан** (прогон не
дошёл до `report.write_json`). Догоняющий прогон того же входа: `SKIP 353, UPDATE 182, NEW 1`,
`bitых чатов: 0`, `.tmp` не осталось. То есть атомарность записи по одному чату держится,
«сдохнуть посередине» безопасно, но прерванный прогон не оставляет отчёта — для UI нужен
свой вывод статуса.

### 7.3 Хэш-нестабильность и «вечный SKIP_LOCAL»

Замерено на чате без меток времени (`qtest-2`, `gaps_report.txt`): после собственной записи
`stored_observed = 91c60438…`, а пересчёт по файлу даёт `a3d90f48…` (content-хэш совпадает).
Следствие: прогон 1 — `NEW`, прогоны 2 и 3 — `SKIP`/`SKIP_LOCAL`, чат «навечно» считается
локально изменённым. Источник: `observed_hash` считается до того, как `_build_doc` подставит
`updated_at = updated or now` (`engine.py:336` против `:401`).

Побочный эффект для LM Studio — описанный в 3.2 «UPDATE-шторм» (182/208 чатов при каждом
повторном импорте папки с тремя копиями экспорта), с плодящимися бэкапами
(у одного чата — 5 файлов бэкапа).

### 7.4 Что отсюда следует для проекта

Минимальный набор гарантий, которых не хватает: (1) уникальные имена tmp; (2) явная блокировка
цели на время записи (`chats\<id>.lock` или advisory-lock рядом с файлом) — сейчас её нет ни в
v1, ни в v2; (3) запрет на одновременный запуск двух прогонов для одного хранилища из UI
(реестр активных задач); (4) исправление порядка вычисления `observed_hash`; (5) стартовый
клининг tmp не трогать, пока имена tmp не станут уникальными и предсказуемыми по префиксу.

## 8. Мелкие дефекты и находки, зафиксированные аудитом (без правок)

Нумерация для отчёта; «минимальное исправление» — оценка объёма, а не выполненная работа.

1. **Обрыв всего прогона при ошибке формата.** `engine.py:245` печатает `{e.code}: {e.message}`,
   но у `AdapterError` (`base.py:13–18`) есть только `code`, сообщение лежит в `Exception.args`.
   Доказательство: одиночный `deepseek_synth.json` → rc=1, отчёта нет; папка `mix` → записаны
   4 чата до обрыва, остальные не обработаны; то же при неверном `--source` и при Markdown-дампе
   без реплик. В `--quiet` ветка печати не выполняется, поэтому тот же вход проходит с
   `parse_errors` в отчёте (проверено на полном прогоне LM-папки).
   Минимальное исправление: `{e}` вместо `{e.message}`.
2. **Фиксированное имя tmp при атомарной записи** → падение при параллельных прогонах (7.1).
   Минимальное исправление: `tempfile.mkstemp(dir=path.parent)`.
3. **`observed_hash` считается до подстановки `updated_at`** → чат без меток времени навсегда
   `SKIP_LOCAL` (7.3). Минимальное исправление: считать хэш после `_build_doc`.
4. **Формат LM Studio `<ts>.chat.json` (ключ только `messages`) не распознаётся** —
   `формат не распознан (уверенность 0.00)`; в папке LM Studio нераспознанными оказываются
   6 из 8 `.json`, включая `.config.chat.json`, `.metadata.chat.json` и sidecar-`*.metadata.json`.
   Минимальное исправление: расширить условие `lmstudio.detect()` и подавить sidecar'ы
   (они не диалоги), либо пропускать их как «не чат» с отдельной строкой отчёта.
5. **rc=0 при ошибках формата.** Явный ZIP → `read: UnicodeDecodeError …`, rc=0; битый ZIP →
   `read: JSONDecodeError`, rc=0; неизвестный флаг `--extract-zip` → `unrecognized arguments`,
   rc=2. При этом rc=2 означает и ошибку аргументов, и `ASSETS_GUARD` (`engine.py:194`) —
   по одному коду возврата эти случаи неразличимы. Минимальное исправление: отдельные коды
   возврата (например 3 — «были ошибки разбора», 4 — `ASSETS_GUARD`) и обязательная сводка
   в конце.
6. **Вложения LM Studio без `--lmstudio-files-dir` становятся `missing` молча** — `preflight_assets`
   (`engine.py:140–177`) проверяет только экспорты ChatGPT. Минимальное исправление: та же
   защита для lmstudio (`user-files` рядом с входом / `~\.lmstudio\user-files`).
7. **Дубликаты одного чата в нескольких файлах.** Действие `DUP` объявлено (`store.py:122`),
   но нигде не используется; несколько копий одного `original_id` в одном прогоне пишут
   в одну цель в порядке сортировки, последний выигрывает, создаются бэкапы.
   Минимальное исправление: сравнение хэшей дублей внутри прогона + строка `DUP` в отчёте.
8. **36 чатов «native» без `source_content_hash`** и 102 чата хэш-версии 2: при первом v2-прогоне
   дают `MIGRATE` (ожиданно, но это надо показать пользователю в предпросмотре).
9. **Неизвестный ключ верхнего уровня `number` в 35 файлах архива** — игнорируется без предупреждения.
10. **UI-путь использует v1, CLI-путь — v2.** Поведение двух точек входа расходится:
    разные форматы, разные хэш-версии, разные статусы. Это и есть главный мотив унификации.

## 11. Что осталось непроверенным (честно)

1. Живой прогон расширения ACE и его форка в одном браузере (пересечение helper'ов) — не проверялся.
2. Пределы `postMessage`/памяти/JSZip (заложенные лимиты 32 МБ/файл, 100 МБ/чат) — не измерены.
3. Живучесть `backend-api/files/download/<id>` для PDF/PY/JSON и старых чатов (53 готовых
   `source_id`) и форма идентификаторов сгенерированных картинок — не проверены.
4. Markdown-экспорт именно ChatGPT (а не LM Studio) и поддержка `conversations.jsonl` от ChatGPT —
   не проверялись.
5. Внутренности v1 `import.py` прочитаны по функциям и хэш-функциям, но прогонами не сверялись:
   чем именно отличаются `compute_content_hash_v1/v2` от v2-хэшей, не установлено.
6. Аномалия `rc=2` при прогоне LM-папки из предыдущей серии: предположение — дублированный
   `--report` в команде (argparse тоже даёт rc=2); отдельно не проверялось.
7. Открытые вопросы предыдущего этапа без ответов пользователя: править ли UI для показа
   ассистентских вложений и плеера; переводить ли видео/аудио на `inline`-раздачу; вводить ли
   новые служебные поля вложений (тогда нужно дополнять `_ATT_META_FIELDS`); порядок подключения
   других платформ после ChatGPT.
