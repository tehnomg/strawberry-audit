# Этап 3 (предварительная подготовка) — три уровня мультимедиа в StrawBerry: что способно храниться, импортироваться и отображаться

Дата замеров: 21.11.2026. Реализация экспортёра и импортёра **не начиналась**: исходники ACE, `ace-fork`, StrawBerry и `import2.py` не изменены, рабочие данные не тронуты.

Проверялись ровно три уровня, как поставил задачу пользователь:

1. **Хранение** — может ли JSON чата описать видео, аудио, документ и произвольный бинарный файл (путь, MIME, имя, размер, статус, связь с сообщением).
2. **Импорт** — способен ли `import2.py` принять эти байты, определить тип и положить в штатную папку `attachments\<имя_чата>\`.
3. **Отображение** — умеет ли интерфейс Strawberry это показать/воспроизвести.

Главный критерий проверки: **экспорт не должен терять бинарные данные только потому, что Strawberry пока не умеет их красиво показывать.**

Отдельно проверялся произвольный файл (не только image/video/audio), чтобы модель вложений была действительно расширяемой, а не списком заранее известных расширений.

**Уровни 1 и 2 выдерживают видео, аудио, документы и произвольные бинарные файлы без потерь — изменений в StrawBerry для этого не требуется.** Провал только на уровне 3 (интерфейс): видео и аудио не воспроизводятся, а вложения ассистентских сообщений вообще не отображаются. Видео (15 586 738 байт, `video/mp4`) и аудио (`audio/x-m4a`, 4 937 923 байта) описаны в JSON корректно — имя, MIME, размер, id, ссылка, — но со статусом `remote`, потому что **в `importer_v2` нет ни одного сетевого запроса** (`grep fetch|urlopen|requests|httpx` по `importer_v2\*.py` — ноль совпадений). Именно поэтому форку нужен свой адаптер, а не «чуть доработать browser_v1».

### Именование и безопасный путь — уже обеспечивают нужное

* Диск: `attachments\<chat_id>\<sha256>.<ext>`, `url = /api/attachments/<chat_id>/<sha256>.<ext>` (`importer_v2\attachments.py:1-7, 234-260`).
* `chat_id = {source}-{sanitize(original_id)}`, где `INVALID_ID_CHARS = [^A-Za-z0-9_-]` (`store.py:22-27`) — точки в chat_id не бывает, поэтому серверные запреты (`value.startswith(".")`, `".." in value`, разрешён только набор `[A-Za-z0-9._-]`, `history-server.py:1333-1347`) автоматически выдерживаются.
* Дедупликация по sha256: повторное копирование тех же байтов не выполняется (`attachments.py:237-239`), повторный импорт не раздувает архив.
* Большое файл читается и пишется потоково чанками 1 МиБ (`attachments.py:248-250`), то есть 15-мегабайтное видео не упирается в память.

### Модель вложений расширяемая, а не список расширений

* `kind` — свободная строка: запись с `kind: "video"` прошла весь путь целиком и легла в архив как есть (проверка `kind_probe`, ниже). Ограничение не в схеме, а в корзинах: у сообщения ровно два списка — `images` и `files`, и именно по ним идут и серверный merge, и UI.
* Ни импортёр, ни сервер, ни UI не имеют белого списка разрешённых MIME/расширений: неизвестный тип → `stats["unsupported"] += 1` и **файл всё равно переносится** (`attachments.py:229-232` с комментарием «сервер отдаст его как поток на скачивание»).

## Уровень 2. Импорт — принимает любые байты, эксперименты в песочнице

### Эксперимент A: 17 типов × 3 способа доставки байтов

`experiments\run_att_types_experiment.py` — вызывается **настоящий** `importer_v2.attachments.stage_attachments`, синтетические байты + реальные jpg/webp из архива Strawberry, каталог вложений — песочничный (`experiments\att_types\attachments`), полный отчёт в `experiments\att_types_report.txt`.

Кейсы: jpg, webp, pdf, png под ложным MIME, webp внутри `.dat` с ложным MIME, **mp4 (ftyp), mp3 (ID3), m4a (ftyp M4A), wav (RIFF WAVE), docx (PK), xlsx (PK)**, **произвольный `.ir`**, **файл без расширения**, `report.final.v2`, `backup.sql.gz`, svg, gif.

Доставка байтов тремя путями, которыми будет пользоваться транспортный ZIP: `_payload` (байты в памяти), `_local_path` (файл на диске), `_asset_ref` + штатный резолвер ChatGPT (байты рядом с JSON + манифест имён `conversation_asset_file_names.json`, `adapters\chatgpt.py:384-414`).

Результат:

| доставка | байт-в-байт совпало |
|---|---|
| `_payload` | **17 из 17** |
| `_local_path` | **17 из 17** |
| `_asset_ref` + манифест | **17 из 17** |

Итоговая статистика прогонов: `staged 17, unique 17, missing 0, unsupported 3 (нет MIME — файл всё равно сохранён), signature_fixed 2`.

Что попутно подтвердилось:

* **Сигнатуры байтов есть только для 5 форматов** — jpg, png, gif, pdf, webp (`attachments.py:41-47`). Для них импортёр сам исправляет ложный MIME/расширение и сохраняет настоящее заявление источника в `declared_mime`: кейс «png, названный .jpg, с MIME image/jpeg» стал `image/png` + `declared_mime: "image/jpeg"`; «webp внутри .dat с именем .jpg» стал `.webp`.
* **Для видео, аудио, docx, xlsx, неизвестных форматов сигнатур нет** — расширение берётся из имени, MIME из заявления источника. Значит требование к нашему экспортёру: имя в JSON обязано нести настоящее расширение, иначе деградирует не содержимое, а только обслуживание (см. ниже про `.bin`/`.dat`).
* Приоритет выбора расширения (`_ext_for`, `attachments.py:102-113`): расширение из `name` → таблица по MIME → `format_hint`/подсказка из имени файла-источника → `bin`. Файл без расширения в имени и без `format_hint`, переданный через `_asset_ref` как `<id>.dat`, лёг на диск как `<sha256>.dat` — байты целые, MIME отсутствует.

### Эксперимент B: весь путь через штатный `import2.py` (песочница)

`experiments\run_engine_sandbox.py`: тот же CLI, что и для рабочих прогонов, но `--chats-dir`, `--attachments-dir`, `--assets-dir` указывают на `experiments\engine_sandbox\`. Источник — пакетный экспорт ChatGPT (`conversations.json` + 5 файлов `<id>.dat` + манифест имён) с пятью вложениями: mp4 400 024 б, m4a 300 028 б, docx 150 008 б, **произвольный `.ir` 7 685 б**, jpg 120 006 б.

Результат первого прогона: `NEW`, `staged 5, reused 0, missing 0, unique_files 5, unsupported 1, warnings []`. Каждый файл на диске **совпал с исходным по SHA256 и по размеру**; в JSON чата у каждой записи появились `sha256`, `size`, `status: "available"`, `url`; у `.ir` — `format_hint: "ir"` и отсутствие `mime`, что не помешало импорту.

Второй прогон того же пакета: `{"SKIP": 1}`, `staged 0, reused 5` — идемпотентность сохранена, дублей нет.

Файл чата содержит `message_id`/`parent_id` (`n1`, `n2`) и штатный набор полей архива (`id`, `source`, `original_id`, `source_content_hash` v3, `parse_report`, `importer_version`) — то есть чат становится обычным чатом StrawBerry.

### Эксперимент C: произвольный `kind`

`kind: "video"` (не `image`/`file`) прошёл `stage_attachments` и лёг в архивное JSON без изменений:

```json
{"kind":"video","source":"strawberry","source_id":"gen1","name":"clip.mp4",
 "mime":"video/mp4","size":50024,"status":"available",
 "sha256":"8df13a43…","url":"/api/attachments/kind-test/8df13a43….mp4"}
```

### Что в `import2.py` всё-таки придётся добавить (единственный блокер транспорта)

* `SUPPORTED_SUFFIXES = (".json", ".jsonl", ".md", ".markdown")` (`engine.py:23`) — `.zip` был бы прочитан как JSON и дал бы `формат не распознан` (уверенность 0.00). Распаковку в транспортном формате надо добавлять: распаковать во временную рабочую область, дальше штатный путь не трогается.
* `preflight_assets()` (`engine.py:140-177`) требует `--assets-dir`, если рядом с входом виден официальный экспорт ChatGPT (манифест или `conversations.json` + `*.dat`), иначе `ASSETS_GUARD` и код возврата 2. Для ZIP это благо: распакованный каталог вложений и есть `--assets-dir`.
* `browser.export-v1` вложения не читает (см. уровень 1) — для нашего формата нужен отдельный адаптер, который наполнит `images`/`files` и поставит `_asset_ref`.

Вывод по уровню 2: **существующий механизм полностью готов принимать видео, аудио, документы и произвольные файлы; менять структуру хранения и систему вложений не нужно.**

## Уровень 3. Отображение — здесь единственные настоящие пробелы

Единственный рендерер сообщений — `msgEl()` в `web\app.js` (строки 817-907); `renderChat()` вызывает его для всех сообщений, включая импортированные чаты (1099-1104). Отдельного просмотрщика импортированных чатов нет; `history-module.js` рисует только список чатов.

Что работает для любого типа:

* **Корзина `files` → чип со ссылкой на скачивание** (app.js 822-845): `href = url`, `download = имя`, в `title` — имя, размер, MIME (`attTitle`, 807-815). Работает для pdf, docx, xlsx, mp4, m4a, `.ir` — чего угодно, с сохранением исходного имени при скачивании. Если байтов нет — чип рисуется без ссылки с подписью «файл не перенесён в хранилище».
* Сервер раздаёт файлы по расширению (`history-server.py:1280-1390`): 5 типов картинок — `inline`; **28 известных типов — с точным Content-Type и disposition `attachment`**, среди них `.pdf .zip .gz .tar .7z .mp3 .wav .ogg .mp4 .webm .mov`; **всё остальное — `application/octet-stream` + `attachment`**, то есть скачивается и не исполняется. Замер по коду для наших кейсов: `.mp4/.mp3/.wav` — точный Content-Type; **`.m4a`, `.docx`, `.xlsx`, `.svg` — octet-stream (скачивание)**; `.ir`, `.bin`, `.v2` — octet-stream. Ничего не теряется ни в одном случае.

Пробелы интерфейса (косметика, не потеря данных):

1. **Нет плеера.** В `web\` нет ни одного элемента `<video>`, `<audio>`, `<iframe>` (`grep` — ноль совпадений; в `index.html` тоже). Видео и аудио можно только скачать.
2. **Картинки в корзине `images` рисуются тегом `<img>`** (app.js 846-879) — если туда положить не-картинку, получится битая иконка. Отсюда обязательное правило нормализатора: **любое не-image медиа кладётся в `files`** (в реальных данных нарушений нет: записей с не-image MIME в корзине `images` — 0 из 3702).
3. **Вложения ассистентских сообщений не отображаются вообще**: ветка `role === "user"` (821-889) рисует и `files`, и `images`, а ветка ассистента (890-905) — только текст и рассуждения. Для ChatGPT это критично по смыслу: сгенерированные изображения и файлы принадлежат сообщениям ассистента, то есть такие вложения будут храниться и скачиваться, но в чате их не видно.
4. **В контекст модели уходят только картинки пользовательских сообщений** (1276-1301) и только те файлы, у которых есть поле `text` (`userText`, 1636-1637). Видео/аудио/бинарь в запрос модели не подставляется — но это поведение модели, а не архива.

Полезная деталь про сохранность полей при правке в UI: сервер восстанавливает клиенту недостающие метаданные вложений по надёжным идентификаторам (`_ATT_META_FIELDS`, `history-server.py:782-784`: `source, source_id, source_ref, url, sha256, size, mime, declared_mime, format_hint, width, height, library_file_id, name, kind, status`), а отбрасывание целого сохранённого чата при спорном сопоставлении сделано намеренно. Клиент (`app.js:761-766`, `history-module.js:607-639`) копирует объекты целиком (`...i`), поэтому **наши новые поля доживают до файла, но сервером не восстанавливаются**: любое поле, критичное для восстановления (например предполагаемое «имя для скачивания»), надо либо вычислять из существующих полей, либо вносить в этот белый список при правке сервера.

## Что это значит для расширяемой архитектуры (уровни: адаптер → нормализатор → пакет → штатный импорт)

Проверенные правила, которые надо зафиксировать в нормализаторе и экспортном пакете (реализация — следующим шагом, сейчас только правила):

1. **Единая внутренняя модель**: сообщение = `role, text, time, message_id, parent_id, reasoning, images[], files[]` (ровно то, что даёт `model.make_message`). Новых полей-корзин не вводить — всё медиа живёт в двух существующих списках.
2. **Правило корзины**: `images` — только то, что браузер покажет тегом `<img>` (png/jpg/webp/gif). Всё остальное — `video`, `audio`, `document`, `binary`, `unknown` — в `files`. Тогда любой тип уже сегодня как минимум скачивается с исходным именем.
3. **`kind`** для совместимости держим `image`/`file`, семантику носим в отдельном поле (`media_type` и т. п.): не-image/MIME, `name` с настоящим расширением, `size`, `sha256`, `source_id` — всё это штатно сохраняется.
4. **`name` обязано нести настоящее расширение**, `format_hint` — страховка. Иначе файл легитимно станет `.bin`/`.dat`: байты целые, но Content-Type и подписи деградируют.
5. **Сигнатуры знает только экспортёр для остальных форматов**: для jpg/png/gif/pdf/webp импортёр сам поправит лживые метаданные, для mp4/mp3/m4a/docx/xlsx/неизвестных — нет. Значит экспортируя, надо определять тип по первым байтам (ftyp/ID3/PK/RIFF WAVE) и давать корректное имя, а не полагаться на то, что «написала платформа».
6. **ZIP-пакет**: JSON чата + каталог байтов + манифест имён в формате `conversation_asset_file_names.json` — родная для резолвера схема (`<asset_id>.dat` и/или исходные имена). Импортёр распаковывает ZIP во временную область и вызывает штатный путь с `--assets-dir` на распакованный каталог. После импорта ZIP не нужен: всё лежит в `chats\` и `attachments\<chat_id>\` со штатными именами.
7. **Контроль целостности на обеих сторонах**: экспортёр кладёт `sha256` и `size` каждого файла в манифест пакета, импортёр пересчитывает их сам (`attachments.py:216-224`) и сверка SHA256 — штатный способ доказать, что бинарные данные не потеряны.
8. **Уровень «отображение» не является блокером.** Если платформа отдаёт видео, а Strawberry его не воспроизводит — данные всё равно сохраняются и скачиваются. Плеер и показ вложений ассистента — отдельная, поздняя правка `web\app.js` + (для inline-воспроизведения) `SAFE_INLINE_IMAGE_MIMES`/`KNOWN_DOWNLOAD_MIMES` в `history-server.py`.

## Уровень 1 (хранение) — подтверждён заново, на новом пути

`chat.json` пакета описывает видео, аудио, документы и произвольный бинарь теми же полями, что и остальной архив: `kind`, `name` (кириллица, пробелы), `mime`, `size`, `sha256`, `status`, `url`, `format_hint`, `source_id`, плюс `source_status`/`fail_reason`, если байты не приняты. Связь с сообщением — вложение лежит внутри конкретного сообщения и знает роль (`user`/`assistant`); `message_id`/`parent_id` сохранены (`node-N`/`node-N-1`). Ограничение не в схеме, а в двух корзинах `images`/`files`: адаптер `strawberry.v1` кладёт в `images` только `kind == "image"`, всё остальное — в `files` (`strawberry_v1.py:319, 236`), и в замере корзина оказалась правильной для всех 14 записей.

**Важная деталь для расширяемой модели:** `kind` в архиве нормализуется до `image`/`file` (строка 319), а любое дополнительное поле записи пакета (`mediaType`, `origin`, `duration` и т. п.) адаптером **не переносится** — в замере `kind: "video"` и `mediaType: "video"` исчезли. Семантику типа носителя несут только `mime` и настоящее расширение в `name`. Отсюда правило для нормализатора: если позже понадобится различать видео/аудио/документ в UI, различать надо по `mime` (или договариваться о новом служебном поле и тогда добавлять его в `_ATT_META_FIELDS` сервера), а не по `kind`.

## Уровень 2 (импорт) — подтверждён заново: правок не нужно

ZIP принимает `import2.py` сам, вложения внутри архива работают через `manifest.json`, `available` появляется только после сверки реальных `size` и `sha256`, байты укладываются в `attachments\<chat_id>\<sha256>.<ext>` с восстановлением исходного имени. Ничего не теряется ни для одного типа, включая те, чью сигнатуру импортёр не знает, и файл без имени вообще. Единственная деградация — косметическая: без настоящего расширения в `name` файл легитимно получает `.dat`/`.bin`, и тогда сервер отдаёт его как `application/octet-stream`, а подпись в UI не показывает тип.

## Уровень 3 (отображение) — за 22.11 не изменился, остаётся единственной дырой

`web\app.js`: ни одного `<video>`, `<audio>`, `<iframe>` (`grep` по `web\` — ноль совпадений; `URL.createObjectURL` встречается только для выгрузки markdown, строка 1493). Функция `msgEl` (строка 817) рисует вложения только в ветке `role === "user"` (821-889: `files` — чип со ссылкой и `attTitle`, `images` — `<img>`), ветка ассистента (890+) — только текст и рассуждения. В замерном пакете 7 из 14 вложений относятся к сообщениям ассистента: они **хранятся и скачиваются**, но в интерфейсе их не видно. Сервер раздаёт без потерь всё: `.mp4/.wav/.mp3` — точный Content-Type + `attachment`, `.m4a/.docx/.xlsx/.svg` и неизвестное (`.ir`, `.dat`) — `application/octet-stream` + `attachment`.
