## 2. A1 — ошибка формата не должна обрывать прогон

**Файл:** `G:\Strawberry\importer_v2\engine.py`

**Причина (подтверждена кодом).** В блоке `except AdapterError` внутри `_run_file`
(строки 239–246) печать обращается к несуществующему атрибуту:

```
245:  print(f"[SKIP] {path.name}: {e.code}: {e.message}")
```

у `AdapterError` (`adapters\base.py:13-18`) есть только `code`, текст сообщения лежит в
`Exception.args`. Исключение из обработчика выходит наружу, а `run()` (строки 197–204)
не изолирует файлы — поэтому падает весь прогон, отчёт не пишется (`import2.py:96-100`
до отчёта не доходит). В `--quiet` та же ветка не выполняется, и тот же вход обрабатывается
штатно с `parse_errors` — отсюда расхождение «с `--quiet` работает, без него падает».

**Минимальные изменения (3 точки):**
1. строка 245: `{e.message}` → `{e}` (`AdapterError.__init__` вызывает
   `super().__init__(message)`, `base.py:16-18`, поэтому `str(e)` — это текст сообщения,
   именно он уже уходит в отчёт на строке 240; код остаётся отдельным полем `e.code`);
2. в `run()` (197–204) вызов `self._run_file(...)` обернуть в `try/except Exception`:
   запись в `stats.errors` вида `{"file": ..., "error": "fatal-in-file: <тип>: <текст>"}`
   и счётчик `FILE_ERRORS` — один «странный» файл больше не останавливает обход папки;
3. в `_run_file` (271–272) вызов `self._import_chat(...)` обернуть в `try/except Exception`:
   запись в `stats.errors` с `id` беседы и счётчик `CHAT_ERRORS` — ошибка конкретной беседы
   (например отказ записи) не обрывает остальные беседы того же файла.

Локализация уже есть для двух других случаев: ошибка чтения (`engine.py:211-218`,
`read_errors`) и общее исключение парсинга (`247-254`, `parse_errors`) — их поведение не меняется.

**Что проверяем:** B1, B2 из базы; добавлены отдельные прогоны на «Markdown без реплик»,
несовпадение с `--source`, файл с битой структурой в середине папки.

**Побочные эффекты:** счётчики `FILE_ERRORS`/`CHAT_ERRORS` новые — печатать их дополнительно
не нужно: `report.summary_text` выводит все счётчики обобщённо (`report.py:79`
«действия: …» по `stats.counts`), поэтому новые имена автоматически попадут и в текстовую
сводку, и в JSON-отчёт (`report.py:67-73`). Формат JSON-отчёта
(`{"summary": …, "chats": […]}`) не меняется.

## 3. A2 — уникальные временные файлы при записи

**Файлы:** `G:\Strawberry\importer_v2\store.py` (чаты), `G:\Strawberry\importer_v2\attachments.py`
(вложения).

**Причина.** `atomic_write` (`store.py:86-107`) использует **фиксированное** имя временного
файла:

```
90:  tmp = path.with_suffix(path.suffix + ".tmp")   # qwen-x.json.tmp
98:  os.replace(tmp, path)                          # 6 повторов по 0.15 с
107: raise RuntimeError(...)                         # если не вышло
```

Два процесса пишут в один и тот же `qwen-x.json.tmp`: побеждает тот, кто раньше сделал
`os.replace`, у второго файл уже переименован → `[WinError 2]` → `RuntimeError` (замер B3:
2 падения из 4). Аналогично в `_stage_one` (`attachments.py:244-251`):
`tmp = dest.with_suffix(dest.suffix + ".tmp")` → `<sha>.<ext>.tmp`, и остаток tmp не удаляется
при исключении.

**Минимальные изменения:**
1. `store.atomic_write`: вместо фиксированного имени — `tempfile.mkstemp(prefix=path.name + ".",
   suffix=".tmp", dir=path.parent)` (уникальное имя с тем же суффиксом `.tmp`), запись через
   `os.fdopen(fd, "w", encoding="utf-8")` с `flush`+`fsync` как сейчас, `os.replace` с той же
   парой повторов, в `finally` — удаление своего tmp, если замена не состоялась. Порядок
   «сначала полностью записали, потом заменили» сохраняется, поэтому атомарность не страдает;
   бэкап по-прежнему создаётся **до** замены (`engine.py:381-383`).
2. `attachments._stage_one`: тот же принцип — unique-имя с суффиксом `.tmp`
   (`dest.name + ".<pid>.<случайные 4 байта>.tmp"` или `tempfile.mkstemp`), `tmp.replace(dest)`
   без изменений, удаление tmp в `finally`.
3. В `store.py` и `attachments.py` добавить `import tempfile`/`os` по необходимости
   (`os` уже импортирован в `store.py`).

**Почему суффикс `.tmp` сохраняется:** чтобы стартовый клининг сервера (A3) продолжал
находить остатки, но уже по возрасту, а не по «одинаковому имени у всех».

**Что проверяем:** B3 из базы (4 процесса) — ожидаем **ноль падений**, ноль остатков `.tmp`,
итоговый файл читаем и байт-в-байт совпадает с однопроцессным результатом; два процесса на
один **тот же sha256** вложения в двух чатах; принудительная занятость целевого файла
(открыть `qwen-x.json` вторым процессом на время замены) — замена должна дождаться или
честно сообщить об ошибке, но не оставить `.tmp`.

**Важное следствие, которое надо принять осознанно:** после A2 параллельные прогоны одного
чата перестают падать, но сохраняют схему «последний записавший победил», и каждый может
создать бэкап. Настоящая блокировка цели (`chats\<id>.lock`) и реестр задач — этап D, там же
правило «из UI одновременно идёт только один прогон». В этапе A фиксируем в отчёте и
документации: **параллельные прогоны безопасны для целостности, но не для «последнего
слова»**.

## 4. A3 — стартовый клининг сервера не должен трогать работу импортёра

**Файл:** `G:\Strawberry\history-server.py`, строки 88–92 (выполняются при импорте модуля,
то есть при каждом запуске сервера):

```
88: for _dir in (CHATS_DIR, BACKUP_DIR, MEMORY_DIR, BASE_DIR / "profiles"):
90:     for _tmp in _dir.glob("*.tmp"):
91:         try: _tmp.unlink()
```

**Риск.** Если в момент запуска сервера работает `import2.py`, сервер стирает его временный
файл → импортёр получает `WinError 2` (тот же сбой, что B3). Отдельно: в `attachments\`
клининг вообще не применяется, поэтому осколки `<sha>.<ext>.tmp` накапливаются.

**Минимальное изменение:** тот же цикл, но удалять только файлы, у которых
`stat().st_mtime` старше порога (предлагается 30 минут), и добавить `ATTACH_DIR` в список
каталогов. Напечатать строку вида `Удалено временных файлов: N (старше 30 мин), пропущено
как свежие: M` — чтобы факт клининга был виден в логе запуска.

**Совместная проверка A2+A3 (требование пользователя):**
1. запуск прогона большой папки в песочнице → на середине прогона вручную выполнить ровно тот
   же фрагмент клининга (в отдельном процессе, с теми же путями, что в песочнице);
2. ожидание: ни один временный файл импортёра не удалён, прогон завершается без `RuntimeError`,
   все записанные чаты читаемы, остатков `.tmp` нет;
3. заранее созданный «старый» tmp (mtime 2 часа назад) удалён; свежий tmp не удалён;
4. повторить для каталога вложений.

**Оговорка:** сервер не перезапускаем без разрешения; правка текста файла применяется только
при следующем штатном запуске `StrawBerry.bat`. Для проверки используется копия фрагмента
в тестовом скрипте, а не живой сервер.

## 5. A4 — порядок вычисления хэша

**Файл:** `G:\Strawberry\importer_v2\engine.py`, строки 335–338 и 373–374, 401.

**Причина.** Хэш наблюдений считается до того, как в документ подставляется дата записи:

```
336: updated = _max(chat.get("updated_at"), _max_time(messages))   # может быть None
338: o_hash = model.observed_hash(title, mdl, archived, created, updated)
401: "updated_at": updated or now                                  # в файл попадает now
```

`recompute_hashes` (`model.py:225`) пересчитывает хэш по файлу, где `updated_at` уже равно
`now` → расхождение (B5) → `local_edited = True` в `store.decide` (`store.py:157`) → при
неизменном источнике действие `SKIP_LOCAL` (B4): чат навсегда считается «правленным человеком».

**Минимальное изменение:** effective-значение `updated_at` вычисляется один раз и используется
и для хэша, и для документа:

```
load = store.load_chat(target)                # перенести выше расчёта хэшей (чтение, безопасно)
updated_eff = updated or (load.data or {}).get("updated_at") or now_eff
o_hash = model.observed_hash(title, mdl, archived, created, updated_eff)
...
"updated_at": updated_eff, "source_updated_at": updated
```

где `now_eff` — одно значение на беседу (уже существующий `now` из `_build_doc` стоит
поднимать на уровень `_import_chat` и передавать в `_build_doc`, чтобы время хэша и время
файла совпадали).

Почему именно так, а не «просто подставить `now` в хэш»: иначе у чатов без меток времени
`updated_at` менялось бы при каждом прогоне, и каждый повтор давал бы `DATE_UPDATE` с
перезаписью и бэкапом. Вариант «взять `updated_at` из существующего файла» даёт: первый
прогон — запись с `now`, повторные — идентичность и `SKIP`.

**Формулу хэша и `HASH_VERSION` (3) не меняем** — существующие 1975 файлов остаются
валидными, миграции не происходит (решение пользователя: массовую миграцию не запускать).

**Что проверяем:** B4/B5 из базы; три прогона подряд одного и того же входа без меток времени
(ожидаем NEW, SKIP, SKIP); три прогона входа с метками времени (ожидаем NEW, SKIP, SKIP);
правки файла в песочнице (оживляем `SKIP_LOCAL`/`CONFLICT` как в `edge_report.txt`, раздел 3) —
эти четыре действия должны остаться различимыми; сверка с реальными файлами архива **только
чтением** (`--dry-run` против копии) — без записи.

**Ожидаемое отличие от базы:** у чатов без меток времени вместо `SKIP_LOCAL` будет `SKIP`.
Уже «помеченные» чаты в рабочем архиве автоматически не чинятся (миграцию не запускаем);
в отчёте этапа будет отдельная заметка, как это чинится точечно: `--force`-прогон конкретного
входа с бэкапом.

## 7. Что специально остаётся прежним (и как это проверяется)

- **Атомарность записи:** по-прежнему «полная запись в временный файл → одна замена».
  Проверка: убийство прогона на середине (B6) — 0 битых JSON, осколки только в `.tmp`.
- **Резервные копии:** создаются до перезаписи, имя `<id>_<дата>_<микросекунды>.json`
  (`store.py:76-83`). Проверка: цепочка `SKIP_LOCAL` → `CONFLICT` → `--force` даёт ровно
  один новый бэкап на факт перезаписи.
- **Идемпотентность:** повторный прогон того же входа не меняет архив (кроме пункта 5 —
  где он должен перестать быть `SKIP_LOCAL`). Проверка: два прогона, сверка sha256 всех
  файлов `chats\` и списка файлов `attachments\`.
- **Вложения:** дедуп по sha256 внутри чата, `url`/`status:"available"` ставит импортёр,
  перенос файлов не меняется (проверено ранее: 51/51 типов байт-в-байт).
- **Формат файлов архива, набор адаптеров, `SUPPORTED_SUFFIXES`, поведение v1** — не меняются.
- **Дубликаты входа** (B8: тройные копии LM-экспорта) после этапа A **останутся** — это
  задача этапа C. После A ожидаем те же `UPDATE`-перезаписи, но без потерь и с бэкапами.
