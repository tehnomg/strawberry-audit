## 3. Что изменилось в поведении

### A1 — прогон не обрывается на несовпадении формата

- Печать ошибки формата исправлена: раньше обращалась к полю, которого у исключения нет, и
  собственный обработчик печати ронял весь прогон. Теперь печатается код и текст ошибки:
  `[SKIP] md_empty.md: markdown_empty: Markdown: нет сообщений в md_empty.md`.
- Добавлен изолятор уровня файла: любое неожиданное исключение при обработке одного входа
  уходит в отчёт (`fatal-in-file: …`) и в счётчик, обход папки продолжается.
- Добавлен изолятор уровня беседы: падение одной беседы не снимает остальные беседы того же
  файла; в отчёт попадает имя файла и `original_id` беседы (`chat-error: …`).
- Новые счётчики: `FILE_ERRORS` (отказ обработки файла), `CHAT_ERRORS` (отказ беседы по
  причине, не связанной с записью), `WRITE_ERRORS` (отказ записи/доступа), `FATAL` (прерванный
  прогон).

### A2 — безопасные уникальные временные файлы

Имя временного файла теперь `<имя>.importer.<pid>.<случайные байты>.tmp` — и для чатов, и для
вложений. Своё осколок удаляется в `finally` всегда. Раньше два процесса писали в одно и то же
`<файл>.json.tmp`: победитель забирал его переименованием, второй падал с `[WinError 2]`.

### A3 — стартовый клининг сервера

Сервер при запуске вычищал **все** `*.tmp` подряд — и мог стереть временный файл работающего
процесса импорта. Теперь в `chats\` и `attachments\` удаляются только файлы импортёра
(маска `*.importer.*.tmp`, рекурсивно) и только старше **30 минут**; свежие осколки
работающих процессов остаются. Прежняя очистка произвольных `*.tmp` сохранена без изменений
для `backup\`, `memory\`, `profiles\` — на рабочие каталоги чистка произвольных `.tmp`
больше не распространяется. Сервер печатает короткий итог клининга
(`[START] Временные файлы импортёра: удалено N …, оставлено как свежие: M`).

Важно: правка вступит в силу **при следующем запуске сервера**. На момент проверки сервер
StrawBerry не был запущен (на порту 8088 никто не слушал), живой процесс не перезапускался.

### A4 — порядок вычисления хэша

Значение `updated_at`, которое подставляется беседам без меток времени, теперь вычисляется
один раз и используется и для хэша наблюдений, и для записываемого документа. Раньше хэш
считался по пустому значению, а в файл уходило «время сейчас» — из-за этого пересчёт хэша по
сохранённому файлу всегда расходился и такая беседа «навечно» получала действие `SKIP_LOCAL`.
Существующее значение из файла переиспользуется, поэтому повторные прогоны не сдвигают дату.

### A5 — коды завершения и отчётность

Сводка и отчёт пишутся в любом исходе (`try/finally`), отчёт создаётся и при фатальном
прерывании. Коды:

| Код | Значение |
|---|---|
| 0 | прогон прошёл без проблем |
| 1 | прогон завершён, есть проблемы входных данных (не прочитан, формат не распознан, ошибка формата, отказ одной беседы) |
| 2 | ошибка аргументов (обрабатывает `argparse`) |
| 3 | остановлено из-за отсутствия необходимых байтов вложений (`ASSETS_GUARD`), чаты не записаны |
| 4 | фатальное прерывание или внутренняя ошибка (отказ записи, отказ отчёта, необработанное исключение) |

Дополнительно в конце вывода печатается одна машиночитаемая строка для будущего окна импорта
(этап D) — разбирать человекочитаемую сводку не придётся:

```
ИТОГ: {"code": 1, "fatal": null, "counts": {...}, "chats": 5, "attachments": {...},
       "errors_total": 3, "report": "…\\rep.json"}
```

Вызовов `import2.py` нет ни в BAT-файлах (v1 работает через `import.py`), ни в сервере, ни в
интерфейсе — смена кодов завершения ничего не ломает.

## 7. Отклонения от формулировки плана и добавления по ходу

1. **Классификация отказа записи.** В плане отказ записи беседы относился к коду 1
   (`CHAT_ERRORS`). Реализовано разделение: `OSError`/`RuntimeError` (не удалось заменить файл,
   отказ диска или доступа) → счётчик `WRITE_ERRORS` → **код 4**; прочие исключения беседы →
   `CHAT_ERRORS` → код 1. Основание — ваше правило «не допускать маскировки фатальных ошибок
   кодом 1». Это единственное содержательное отклонение от текста плана.
2. **Машиночитаемая строка `ИТОГ:`** добавлена в вывод как часть пункта A5
   («однозначные коды завершения и отчётность») — она понадобится окну импорта на этапе D.
   Человекочитаемая сводка осталась без изменений.
3. **Проверка штатного прерывания.** Изначально R12 пытался посылать дочернему процессу
   Windows `CTRL_BREAK_EVENT`; эксперимент (`experiments/run_stageA_probe3.py`) показал, что
   такой сигнал рвёт процесс на уровне ОС с кодом `0xC000013A` и без завершения кода Python,
   поэтому отчёт не появляется. Проверка переписана на внутрипроцессный `KeyboardInterrupt`
   (именно это даёт Ctrl+C в консоли): код 4 и отчёт получены. Ограничение зафиксировано
   честно, архитектура не менялась, дополнительных обработчиков сигналов в код не добавлялось.
4. **`importer_v2/report.py` не изменялся** — как и было оговорено («только если действительно
   потребуется»): сводка печатает словарь счётчиков обобщённо, новые счётчики появились сами.
