### 1.2 Имена

Схема одна и та же в обоих каталогах, без исключений (148/148 и 486/486):

```
<метка времени мс> - <исходное имя файла>          пример: 1735763503873 - 822.jpg
```

в двух корнях» на этих данных нет; порядок поиска всё равно должен быть
детерминированным, иначе он станет вопросом случая на другой машине.

### 1.3 Sidecar `*.metadata.json` — недоиспользованный источник проверки

Ключи: `type`, `sizeBytes`, `originalName`, `fileIdentifier`, `preview{data}`, `sha256Hex`.
Проверено на реальных файлах:

  оригинала**, не уменьшек: отношение превью/оригинал = 1.000 (примеры:
  `image/jpeg` 2 442 427 б против файла 2 442 427 б);
- `originalName` — настоящее имя, данное пользователем
  (`gpt3.5оподмывании.txt`, `Только небо, только ветер….docx`); у 57 из 81 записей

- у каждого payload есть sidecar, «осиротевших» sidecar без файла — 0.

«Осиротевшие» файлы по имени (не упомянуты ни в одной беседе): соседняя копия — 91

## 2. B. Где в JSON лежат записи вложений

### 2.1 Формат беседы

Одна беседа = один файл `<ts>.conversation.json`, ключи:
`name, systemPrompt, messages[], createdAt, clientInputFiles[], userFilesSizeBytes,
lastUsedModel, notes`, плюс (не во всех) `preset, plugins, pluginConfigs,
disabledPluginTools, looseFiles, userLastMessagedAt, assistantLastMessagedAt`.

Замеры по беседам:

| Вход | Файлов | Уникальных `createdAt` | Файлов, где имя ≠ `createdAt` | Без `createdAt` |
|---|---|---|---|---|
| `G:\Strawberry\import\conversations` (рекурсивно) | 543 | 333 | 107 | 0 |
| `C:\Users\User\.lmstudio\conversations` | 254 | 254 | 73 | 0 |

Структура папок экспорта: 132 файла в корне + `Migrated` 200 + `Migrated (2)` 105 +
`Migrated (3)` 105 + `история в больнице` 1 (`декабрь24` пустая). Копии: **105 id
встречаются ровно в трёх копиях** (`Migrated`, `(2)`, `(3)`), 228 id — по одному разу;
корень и `Migrated` не пересекаются (0 общих id). Различий по содержимому между копиями
нет — отличаются только служебные пути (`perChatPredictionConfig`, `stepIdentifier`,
наличие `preset`/`lastUsedModel`), см. п. 5.

Имя файла ≠ createdAt более чем в пятине файлов, поэтому идентификатор надо брать
из `createdAt` (так и делает адаптер), а не из имени файла. Случайных коллизий
`createdAt` между разными беседами нет (333 уникальных значения на 333 уникальных id).

### 2.2 Единственный надёжный носитель вложения — content-части сообщений

Путь: `messages[].versions[].content[]`, плюс `versions[].preprocessed.content[]`
и у `multiStep` — `steps[].content[]`. Часть вида `type:"file"`.
Всего content-частей: экспорт 22 079 `text` + 81 `file`; локальные 89 959 `text` +
391 `file` + 46 `toolCallRequest` + 40 `toolCallResult` (инструментные части адаптер в
`reasoning` сводит уже на этапе разбора).

Две формы записи, обе встречаются:

```jsonc
// форма 1 — без имени (57 записей экспорт / 243 локальные)
{"type": "file", "fileIdentifier": "1735770588997 - 551.jpg",
 "fileType": "image", "sizeBytes": 222330}

// форма 2 — с именем (24 / 148)
{"type": "file", "name": "Рисунок1.jpg", "identifier": "1735763503873 - 822.jpg",
 "fileType": "image", "sizeBytes": 21460}
```

`fileType` — псевдо-MIME LM Studio, не MIME: `image`, `text/other`, `application/word`,
`unknown`. Ключ-идентфикатор: `fileIdentifier` **или** `identifier` (адаптер и берёт
одно из двух — это правильно).

Чат-уровневые списки **не годятся как источник**: `clientInputFiles` присутствует у всех
543/254 файлов и пуст во всех; `looseFiles` присутствует у 128 файлов экспорта и у 254
локальных — и тоже пуст во всех.

Отдельно: части `type:"image_url"` с `data:image/...` (вставленные в LM картинки)
содержат байты внутри JSON и попадают в архив без `user-files` — в D3 так ушли 16 из 16
записей без всякого флага.

## 3. C. Что делает код сейчас и чем это плохо

Текущая цепочка (`importer_v2/adapters/lmstudio.py:18–47, 244–291`,
`import2.py:39–40, 73–76`, `engine.py:96, 108–116`):

1. один корень: `--lmstudio-files-dir`; если не задан — `~\.lmstudio\user-files`,
   если существует;
2. поиск: `files_dir / identifier` и `is_file()`; в Windows это срабатывает и при
   **другом регистре** имени;
3. `sizeBytes` из JSON **не сверяется**; в архиве `size` всё равно перезаписывается
   фактическим (`attachments.py:225–226`), так что следов расхождения не остаётся;
4. если файла нет — пробуются `<id>.json` / `<id>.metadata.json`, и если там
   `preview.data` начинается с `data:image/`, в архив идут байты превью
   (для картинок это полные байты, так что приёмлемо);
5. `sha256Hex` и `originalName` из sidecar **не читаются**;
6. вложение с `name=None` уходит в архив без имени (для 57/81 и 243/391 записей).

Доказательства фикстурами (`stageB_scenarios_report.txt`, п. C):

- запись `sizeBytes: 5000`, в указанном корне файл на 1200 б → прогон `rc=0`,
  вложение `status=available`, в архиве `size=1200` — **молчаливая подстановка**;
- запись `9999000000002 - doc.txt`, на диске `9999000000002 - Doc.TXT` (27 б вместо 14) →
  принято как есть, `status=available`;
- имитация правильных правил на тех же фикстурах
  (`stageB_scenarios2_report.txt`, п. C): несовпадение размера → переход к следующему
  корню и поиск там (найден корректный файл на 5000 б), «только регистр» → отдельный
  статус, отсутствие → `не найден`.

## 5. E. UPDATE-шторм: причина установлена, место исправления — движок, не адаптер

Замер на 30 беседах, присутствующих в трёх копиях экспорта
(`stageB_scenarios_report.txt`, п. E):

| Прогон | Действия | Бэкапов |
|---|---|---|
| 1-й (три копии в одном входе) | `NEW 30, UPDATE 30, SKIP 30` | 30 |
| 2-й | `UPDATE 60, SKIP 30` | 90 |
| 3-й | `UPDATE 60, SKIP 30` | 150 |
| контроль: одна копия, прогон 1 / 2 | `NEW 30` / `SKIP 30` | 0 |
| контроль: две копии, прогон 1 / 2 | `NEW 30, UPDATE 30` / `UPDATE 60` | — |

Причина — одно поле, `model`:

```
копия Migrated:       model = "lmstudio"            (нет preset, lastUsedModel, senderInfo)
копия Migrated (2):   model = "bartowski/aya-23-8B-GGUF/aya-23-8B-Q8_0.gguf"
копия Migrated (3):   model = "bartowski/aya-23-8B-GGUF/aya-23-8B-Q8_0.gguf"
original_id во всех копиях одинаков (= createdAt), тексты сообщений идентичны
content_hash A vs B:  РАЗЛИЧАЕТСЯ;  B vs C: совпадает
content_hash без поля model: A vs B совпадает, B vs C совпадает
```

То есть копии не «конфликтуют» по содержимому: одна из них экспортирована более старой
версией LM Studio и просто **не содержит сведений о модели**, а адаптер
(`lmstudio.py:157–162, 172`) подставляет служебную заглушку `"lmstudio"`. Хэш содержимого
включает `model` (`model.py:188–205`), поэтому внутри прогона копии пишут в один файл
по очереди (порядок сортировки: A → B → C), а на следующем прогоне хэш архива снова
не совпадает с хэшем копии A → два `UPDATE` на беседу на каждый прогон и по бэкапу
на каждый `UPDATE`. На реальном архиве это 105 бесед × 2 = 210 перезаписей на прогон.

Где правильно лечить (обоснование, а не привычка):

- **не в адаптере**: адаптер видит один файл и не знает, что в том же прогоне есть
  другие копии того же `original_id`;
- **уровень 1 — движок/диспетчер (этап C)**: группировка записей с одинаковым
  `original_id` внутри одного прогона → один победитель, остальные `DUP`
  (действие объявлено в `store.py:122` и никогда не присваивается);
- **уровень 2 — движок (этап C)**: правило монотонности информации — не понижать
  известное значение `model` до служебной заглушки (в терминах хэша: при равенстве
  «остального» содержимого считать копию не отличающейся);
- **что относится к этапу B**: адаптер должен *сообщать*, откуда взята модель
  (`senderInfo.senderName` / `lastUsedModel.identifier` / `preset` / заглушка), —
  это поле `parse_report["model_source"]` и отдельный счётчик в отчёте. Без него
  правило монотонности в этапе C будет гадать.

Этап B **не** устраняет шторм полностью: без правил движка копии продолжат писать
по 2 `UPDATE` на прогон. Это надо учесть при очерёдности: шторм обязан быть закрыт
до первого общего прогона по архиву.
