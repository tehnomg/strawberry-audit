# Этап B — технический план: вложения LM Studio и подготовка к лечению UPDATE-шторма

Документ — **план**, реализация только после согласования. Основа — замеры из
`STAGE_B_LMSTUDIO_AUDIT.md` (нумерация дефектов там же: продолжение раздела 8
`STAGE3_IMPORT_ARCHITECTURE.md`).

Объём оценки — правки «здесь и сейчас», без рефакторинга: диспетчер входов (этап C)
потом заменит классификацию входов в движке, и уже заложенные счётчики сохранит.

## 1. Правила, которые реализует этап B

### 1.1 Порядок поиска байтов (дефект 6)

Корни, в порядке приоритета, дедуплицированные по реальному пути:

1. явный `--lmstudio-files-dir` (если задан — всегда первый);
2. `<выбранный вход>/user-files`, если вход — папка (переносимый пакет);
   если вход — файл, то `<папка файла>/user-files`;
3. `<родитель выбранного входа>/user-files` (сейчас так лежит `import\user-files`
   рядом с `import\conversations`);
4. `~\.lmstudio\user-files` (текущий неявный дефолт, остаётся последним).

Первый корень, где файл проходит **все** проверки п. 1.2, и есть результат.
Если ни один корень не подошёл — вложение `missing` + явная строка в отчёте со списком
просмотренных корней. Молчание запрещено (принцип этапа A).

### 1.2 Сопоставление файла с записью (B-1, B-2, B-3)

Кандидат принимается, если выполнены все условия:

1. `path.name == identifier` **посимвольно** (не `exists()`: в Windows путь открывается
   и при другом регистре; зафиксировано фикстурой `Doc.TXT`);
2. `path.stat().st_size == sizeBytes`, если `sizeBytes` указан в записи;
3. если рядом есть `<identifier>.metadata.json` с `sha256Hex` — хэш файла обязан совпасть
   (на реальных данных 50/50 проверок совпали, `sha256Hex` есть у 243/243 локальных
   и 64/74 экспортных sidecar'ов).

Любое несовпадение → этот корень отвергается, поиск продолжается в следующем;
если корни кончились — статус `missing`, в отчёт попадают оба размера
(ожидали `5000`, нашли `1200`) и путь кандидата. Никакой подстановки «похожего» файла.

Дополнительно, только если файла-вложения нет нигде, а sidecar есть: байты берутся из
`preview.data` (проверено: это полные байты оригинала, отношение 1.000), но только для
`data:image/...`, и такое вложение помечается счётчиком `from_sidecar_preview` — чтобы
было видно, откуда взялись байты.

### 1.3 Имя и тип (B-4, B-6)

Если у записи нет `name`/`originalName` (57 из 81 записей экспорта, 243 из 391 локальных),
имя берётся из sidecar-поля `originalName`; если и там пусто — из имени идентификатора
после ` - `. `fileType` остаётся псевдо-MIME LM Studio (`image`, `text/other`,
`application/word`) — его кладём в `declared_type`, а настоящий `mime` определяет
`attachments.sniff_signature` по байтам, как уже делает.

### 1.4 Отчёт (B-5)

Новый блок `stats.lmstudio`:

```json
{"roots": ["…", "…"], "found_by_root": {"tier2": 10, "tier4": 16},
 "size_mismatch": 0, "case_only": 0, "from_sidecar_preview": 3,
 "sha_mismatch": 0, "records": 27, "missing": 0}
```

Он попадает в JSON-отчёт, в текстовую сводку одной строкой
(`LM Studio user-files: корни …; найдено …; без байтов …`) и в машиночитаемую строку
`ИТОГ: {…}` в `import2.py` (поля `LM_MISSING`, `LM_SIZE_MISMATCH`).

### 1.5 Легаси-формат `*.chat.json` и sidecar'ы (дефект 4)

- `*.metadata.json`, `*.config.chat.json`, `*.metadata.chat.json` внутри папки LM Studio —
  классифицировать как **«не чат»** с причиной `sidecar_of_chat_file`, считать отдельным
  счётчиком `not_a_chat`, не считать ошибкой формата;
- `<ts>.chat.json`: разбирать как легаси-беседу (id — из `identifier` соседнего
  `*.metadata.chat.json`, а не хэш от содержимого), **только** если в этом же входе нет
  беседы с таким же id (замер: 105 из 106 семейств уже покрыты `.conversation.json`,
  не покрыто одно — `1777470656790`). Иначе — `not_a_chat` с причиной
  `legacy_duplicate_of_conversation`.

Итог по шуму: 318 строк «формат не распознан» и `rc=1` → 0 ошибок формата,
1 новая беседа, `rc` определяется только реальными проблемами.

### 1.6 Подготовка к этапу C (шторм, дефект 7)

В этапе B — только данные для решения, не само решение:

- `parse_report["model_source"]` ∈ `senderInfo` / `lastUsedModel` / `preset` / `placeholder`
  и счётчик `chats_model_placeholder` в сводке;
- тесты T-B13…T-B15 фиксируют текущее поведение шторма, чтобы этап C имел точку отсчёта.

Само устранение (`DUP` для копий одного `original_id` внутри прогона + запрет понижения
известного `model` до заглушки) — **этап C**, потому что адаптер видит один файл и не может
знать о других копиях.

## 4. Риски и как их снимаем

| Риск | Реальность на наших данных | Снятие |
|---|---|---|
| Новый порядок корней изменит байты, взятые при повторном импорте → волна `UPDATE` | Пересечение имён между корнями **0 файлов** → на этой машине изменений не будет | перед первым прогоном — `--dry-run` и сверка счётчиков; `sha256` в архиве уже есть, совпадающие байты дают `reused`, а не перезапись |
| Точное сравнение имени отбракует файлы, которые раньше «проходили» | 0 случаев различия регистра (замер 634 файлов) | тест T-B7; при обнаружении — отдельная строка отчёта, а не молчаливый отказ |
| Сверка `sizeBytes` отбракует вложения, размер которых в LM изменился после экспорта | 0 несовпадений на 472 реальных записях | тест T-B6; при несовпадении пробуем следующий корень, потом `missing` |
| Сверка `sha256Hex` может отбраковать часть вложений | `sha256Hex` есть не везде (64/74 экспортных), но в 50/50 проверок совпал | проверка только при наличии хэша; расхождение — предупреждение + `missing`, не падение прогона |
| Смена классификации sidecar'ов меняет `rc` с 1 на 0 для папки LM Studio | Да, измерено | зафиксировать в отчёте и в документации форматов; BAT/сервер `import2.py` не вызывают |
| Легаси-парсинг `.chat.json` может создать дубли бесед | 105 из 106 семейств уже покрыты | правило «только если не покрыто» + T-B17; покрытие проверяется по id из `metadata.chat.json` |
| Этап B не убирает шторм, и пользователь может ожидать его здесь | Шторм = 210 перезаписей на прогон на реальном архиве (105 бесед × 2) | прямо сказано в отчёте: сначала этап C (правила движка), потом общий прогон архива |
| Общий прогон по архиву до этапа C | 141 чат без `importer_version` → `MIGRATE`; + шторм | порядок: B → C → общий прогон; до C архив не перегонять |

## 5. Критерии приёмки этапа B

1. Все три раскладки (D1/D2/D3) дают **полный** перенос вложений без ручного флага:
   `missing = 0` там, где байты физически есть; `missing = записи` там, где их нет,
   и отчёт называет просмотренные корни.
2. На реальном срезе (20 записей из `import\conversations` и 25 локальных записей)
   разрешаются 100 % записей, повторный прогон даёт `reused`, новых файлов в
   `attachments` 0, `UPDATE` 0, бэкапов 0.
3. Ни одного молчаливого принятия «не того» файла: фикстуры B6/B7/B8 дают
   `missing`/`size_mismatch`/`case_only`/`sha_mismatch` со значениями из матрицы.
4. У 0 вложений пустое имя среди 472 реальных записей (было 300 без имени).
5. Папка LM Studio с легаси-форматом: `parse_errors = 0`, `not_a_chat = 317`,
   легаси-беседа импортнута ровно один раз, `rc` без ложной ошибки.
6. Регресс этапа A зелёный (68 + 135 + 99 проверок), рабочий архив не изменён
   (2113 чата, 332 папки вложений / 1233 файла — контрольная сверка до и после).
7. Документация обновлена: `docs/DATA_FORMATS.md` — раздел про LM Studio
   (формат беседы, где лежат вложения, схема имён `user-files`, sidecar, правила поиска).

## 6. Что нужно решить перед реализацией

1. **Блокировать или предупреждать**, если ни один корень `user-files` не найден?
   Предложение: предупреждение + счётчики (как сейчас для ChatGPT без `--assets-dir`
   он блокирует только при недоступности *указанного* каталога) — для LM блокировки нет,
   иначе D3-подобные частичные переносы станут невозможны.
2. **Легаси `.chat.json`**: предложенный вариант (подавить sidecar'ы, легаси разбирать
   только для непокрытых — +1 беседа) или полностью не поддерживать
   (тогда 106 семейств старых выгрузок в архив не попадут никогда).
3. **Шторм**: оставляем строго этапу C (в этапе B только `model_source` и тесты)
   или добавляем в этап B точечное правило движка «не понижать `model` до заглушки»
   (≈6 строк в `engine.py` + тест) — это снимет 210 перезаписей на прогон уже сейчас,
   но частично залезет в зону ответственности этапа C.
