## 2. Правила склейки (что именно реализовано)

1. **Основание группы** — одинаковый `createdAt` у двух и более файлов
   `*.conversation.json` **в пределах одного прогона**. Сам по себе одинаковый
   `createdAt` беседы не склеивает: это только кандидат.
2. **Отпечаток существенного содержимого** (`substance_of` в адаптере LM Studio):
   название, системный промпт, `clientInput`, заметки, а по каждому сообщению —
   индекс выбранной версии, роль, тип и содержимое **всех** версий (тексты;
   идентификатор/тип/размер вложений). Не входят: `lastUsedModel`, пресеты,
   `perChatPredictionConfig`, `tokenCount`, `pinned`, метки времени, размер и имя
   файла — именно ими копии одной беседы в выгрузке и отличаются (замер: 105 групп
   по 3 копии). Различия в *невybранных* версиях тоже попадают в отпечаток:
   молча терять их нельзя.
3. **Выбор основной копии — до первой записи и независимо от порядка обхода:**
   больше сообщений → больше записей вложений → есть известная модель → первая по
   имени пути. Порядок участников внутри группы приводится к сортировке по пути,
   поэтому результат одинаков, передан ли вход каталогом или списком файлов.
4. **Исход для неосновных копий:**
   * отпечаток совпал → `DUP`;
   * пустая оболочка (0 сообщений) при полной копии **с тем же названием** → тоже
     `DUP` (требование приёмки к группе `1726623283209`);
   * иначе → `DUP_SUSPECT`: пишется только основная копия, остальные не записываются,
     в вывод и отчёт уходит предупреждение и причина; автоматической склейки нет.
   Ни файл чата, ни резервная копия для `DUP`/`DUP_SUSPECT` не создаются.
5. **Модель не понижается.** При равном содержимом основной становится копия с
   известной моделью: иначе копия без `lastUsedModel` (заглушка `lmstudio`)
   записалась бы первой, а настоящая копия стала бы `DUP` — модель потерялась бы,
   несмотря на правило `kept_model` этапа B. `kept_model` (этап B) не сломан и
   работает как раньше.
6. **Разные беседы с одним `createdAt`** не склеиваются в одну запись: содержательнее
   копия импортируется, вторая помечается `DUP_SUSPECT`; потерь нет — исходные файлы
   на месте, оператор видит предупреждение и код 1.
7. **Служебные уровни не перепутаны:** `LEGACY_DUP` (легаси-семейства, этап B),
   `not_a_chat` (sidecar'ы) и `DUP` (копии) — разные счётчики, один вход попадает
   ровно в один из них.

## 3. Как это устроено в коде

Шаг 1. `ImportEngine._lm_dup_plan(files, stats)` (`engine.py:219-301`) —
предрассматривает входы **до** обхода: для каждого `*.conversation.json` читает JSON
(тот же приём, что уже делал `_lm_covered_ids`), берёт `createdAt`, считает
`substance_of`, помечает наличие известной модели. Группы из двух и более участников
попадают в план `self.lm_plan` и в индекс `self._lm_dup_by_path`
(путь → `участник`, `основная копия`, `createdAt`). Стоимость — повторное чтение
LM-входов: на всей выгрузке (544 файла, 58 МБ) это доли секунды на файл, полный
прогон с склейкой быстрее прежнего (меньше записей и бэкапов).

Шаг 2. `ImportEngine._dup_action(me, win)` (`engine.py:303-319`) — единая точка
определения `DUP` / `DUP_SUSPECT` и человекочитаемой причины; её же использует план,
чтобы заранее предупредить о группе с противоречием.

Шаг 3. `ImportEngine._lm_dup_for_path(path)` (`engine.py:321-339`) — решение по
конкретному файлу входа. Оно берётся из плана (то есть из исходного JSON), а не из
результата адаптера: пустую оболочку адаптер отвергает как «0 бесед», и без плана она
числилась бы ошибкой разбора.

Шаг 4. Подключение в `_run_file`:
* `engine.py:635` — в ветке отказа адаптера (`AdapterError`) копия группы
  оформляется как `DUP`/`DUP_SUSPECT`, а не как `parse_errors`;
* `engine.py:677` — перед импортом каждой беседы: если файл — неосновная копия,
  вызывается `_record_lm_dup` и беседа не доходит ни до записи, ни до бэкапа.
  Разбор адаптером при этом выполняется (счётчики поясов вложений этапа B
  сохраняются), но байты переносятся один раз.

Шаг 5. Учёт: `_record_lm_dup` (`engine.py:341-360`) поднимает счётчик действия и
пишет запись в `stats.chats` с причиной, указанием основной копии (`dup_of`) и
отпечатками (`substance` / `kept_substance`) — это видно в JSON-отчёте прогона.

## 7. Отличия от аудита C1 и уточнения

1. **Отдельного модуля `importer_v2\grouping.py` нет** (аудит предлагал ~150 строк):
   группировка живёт в `engine.py`, отпечаток — в адаптере `lmstudio.py`. Отдельный
   модуль заставил бы второй раз разбирать вход и угадывать формат; отпечаток знает
   только адаптер формата. Имя тестового набора оставлено по аудиту —
   `tests\test_lmstudio_merge.py`.
2. **`store.py` тронут чуть больше, чем планировалось** («только использование `DUP`»):
   в `ACTIONS` добавлен `DUP_SUSPECT`, иначе пофайловые счётчики действий в отчёте
   его не показывают.
3. **Пустые оболочки стали `DUP`, а не `parse_errors`** (аудит ожидал `parse_errors`):
   так требует граница C1 №2 и приёмка по группе `1726623283209`. Побочный эффект —
   `parse_errors` на реальном срезе 11 → 9.
4. **Разные беседы с одним `createdAt`**: аудит ожидал две записи через
   `store.collision_id`; принятоe решение C0 №4 — писать только лучшую копию,
   остальные `DUP_SUSPECT` без записи. Реализовано по решению C0.
5. **Уточнён код возврата для `DUP_SUSPECT`.** В `STAGE_C0_DECISIONS_AND_CONTRACTS.md`
   было два места с разной формулировкой (строка 130 относит `DUP_SUSPECT` к проблемам
   входов со кодом 1, строка 136 — «кода не портят»). Принято: `DUP_SUSPECT` даёт
   **код 1** (вход не перенесён автоматически — оператор должен это увидеть),
   `DUP` кода не портит. Формулировка в C0-документе уточнена точечно.
6. **Число групп и `DUP` оказались больше согласованного диапазона 206…208.**
   Независимый замер выгрузки: файлов `*.conversation.json` — **544** (не 543),
   уникальных `createdAt` — 333, групп с >1 файлом — **106**: 105 групп по 3 копии
   и **одна пара** — `1787399266109` (`conversations\1787399266108.conversation.json`
   и `conversations\история в больнице\1787399266108.conversation.json`, оба
   1 356 522 байта, отпечатки совпадают; имя файла ≠ `createdAt`). Участников — 317,
   неосновных — **211**. Диапазон 206…208 предполагал, что пустые оболочки останутся
   ошибками разбора (211 − 2 = 209, минус ещё нерассортированные отказы). По принятой
   границе C1 №2 оболочки — `DUP`, поэтому 211. Арифметика закрыта инвариантом
   `dup_group_members − dup_groups == dup_members`.
7. **Счётчики поясов вложений (`records`, `resolved`, `sidecar_preview`) считаются по
   всем копиям**, байты переносятся один раз. Это сознательное сохранение базы этапа B
   (58 записей / 58 разрешено — не изменилось); иначе отчёт перестал бы показывать,
   что было в отброшенных копиях.
8. **Новое решение в рамках границы C1 №5:** приоритет копии с известной моделью при
   равном содержимом (см. раздел 2.5). Иначе настоящая модель терялась бы, когда

## 9. Открытые вопросы (для следующих подэтапов)

1. Склейка работает **в пределах одного прогона**. Если оператор запустит копии
   разными прогонами, вторая копия станет `SKIP`, а не `DUP` (данные те же, записей
   не прибавляется). Нужно ли считать такие прогоны одним заходом — вопрос к
   диспетчеру входов (C4).
2. Для `strawberry.v1` (C3) группировка должна опираться на `conversationId`, а не на
   `createdAt`; план C1 делает это тривиальным: основание группы — поле входа,
   отпечаток — содержимое.
3. Спорные пары с разными содержимыми (`DUP_SUSPECT`) сейчас не получают второго
   файла архива. Если понадобится «сохранить обе как разные беседы», это надо
   согласовать отдельно (там нужен `collision_id` и решение о именах).
4. `DUP`-копии по-прежнему разбирать и считать — это время на больших выгрузках; если
   станет медленно, разбор можно пропускать по плану (счётчики поясов тогда
   изменятся — нужно решение).
