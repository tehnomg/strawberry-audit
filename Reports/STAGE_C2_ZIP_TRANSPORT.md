# Этап C2 — ZIP как транспортный контейнер

Дата: 2026-11-21. Основание: разрешение «теперь занимаемся исключительно ZIP как
транспортным контейнером» после приёмки C1, с перечнем из десяти разрешённых работ
и ограничением «если ZIP превышает лимиты или содержит опасную запись, отклоняется
весь архив. Никакого частичного импорта его содержимого».

Смежные документы: `STAGE_C_AUDIT_SPEC.md` (раздел 2 и итог C2),
`STAGE_C0_DECISIONS_AND_CONTRACTS.md` (контракты и коды выхода),
`STAGE_C1_LM_DEDUP.md` (дедупликация — в C2 не менялась).

---

## 1. Итог

ZIP-архив стал полноценным входом импортёра v2: пользователь может указать один
файл `.zip` (или выбрать папку, где архив лежит) — импортёр распаковывает его во
временную область и передаёт файлы существующему механизму разбора, вложений и
дедупликации. Никакого нового формата и никакого частичного импорта: архив либо
принимается целиком, либо отклоняется целиком с явной причиной.

Сделано:

- новый модуль `importer_v2\container.py` (346 строк): определение архива по
  сигнатуре, проверка имён записей (zip-slip, абсолютные пути, drive-буквы,
  недопустимые символы, устройства, симлинки, спецфайлы, шифрование), лимиты,
  проверка свободного места, потоковая запись через `.tmp`, восстановление
  `mtime` из `ZipInfo`, удаление распакованного при любой ошибке;
- встройка в `importer_v2\engine.py`: распаковка **до** `preflight_assets` и до
  сбора входов, блок `containers` в статистике, поле `container` у каждой записи
  входа, поля `source_container*` в архивной беседе, очистка области в `finally`;
- `import2.py`: флаги `--unpack-dir`, `--keep-unpacked`, `--zip-max-entries`,
  `--zip-max-total-mb`, `--zip-max-entry-mb`; уборка сирот в `%TEMP%` при старте;
  счётчик `ZIP_ERRORS` → код возврата 1; ключ `containers` в строке `ИТОГ:`;
- `report.py`: печатный и JSON-блок «ZIP-контейнеры» (сколько принято, записей,
  байт, отклонено, лимиты, где область, что отклонено и почему);
- тесты `importer_v2\tests\test_zip_transport.py`: 18 кейсов матрицы T-Z,
  **195 проверок, 0 провалов, 0 пропусков**;
- регресс этапов A/B/C1 не сломан: суммарно **696 проверок, 0 провалов,
  13 пропусков** (было 501);
- приёмка на реальном срезе (`experiments\stageC2_acceptance_run.txt`):
  **21 проверка, 0 провалов** — ZIP и распакованная папка дают одинаковые

## 2. Правила: что именно реализовано

### 2.1 Как вход понимается как архив

| ситуация | поведение |
|---|---|
| файл начинается с `PK\x03\x04` | архив, независимо от расширения (`выгрузка.zip`, `выгрузка`, `.docx`) |
| `PK\x05\x06` (пустой центральный каталог) | отказ `zip_empty`: «архив без единой записи» |
| `PK\x07\x08` (split/многотомный) | отказ `zip_spanned`: многотомные архивы не поддерживаются |
| расширение `.zip`, но сигнатура другая | обычный вход: разбор и, если это не чат — запись с причиной (`read_errors`) |
| архив лежит внутри выбранной папки | найден обходом `rglob` по `.zip` + проверкой сигнатуры, распакован; счётчик `zip_in_folder` |
| архив без единого файла поддерживаемого формата (`.docx`, `.epub`, `.jar`) | распакован, чатов нет: счётчик `without_chat_files` и запись `not_a_chat` — вход не исчезает молча |
| ZIP внутри архива | **не** распаковывается автоматически; записан в `nested` контейнера, в списках входов — `not_a_chat`, счётчик `zip_nested` |

### 2.2 Лимиты и свободное место

Значения по умолчанию и флаги:

- записей в архиве — не больше **20 000** (`--zip-max-entries`);
- суммарный размер распакованных данных — не больше **4 ГиБ**
  (`--zip-max-total-mb`, по умолчанию 4096);
- размер одной записи — не больше **512 МиБ** (`--zip-max-entry-mb`, по умолчанию 512);
- перед записью проверяется свободное место: должно быть не меньше заявленного
  размера плюс запас **64 МиБ** (`FREE_MARGIN_BYTES`, `container.py:45`) → иначе
  отказ `zip_space`.

Проверка идёт по **заявленным** размерам центрального каталога, до записи первого
байта: архив с обманными размерами не успевает занять диск. Фактический размер
при записи дополнительно контролируется потоково (`_write_entry`, `container.py:308`):
запись длиннее заявленной → отказ.

### 2.3 Опасные записи и имена

Отказ всего архива (`zip_*` — код причины в отчёте):

- `zip_slip` — после канонизации (`os.path.abspath`) путь выходит за корень
  распаковки (`..\..`, `a\..\..\b`);
- `zip_traversal` — ведущее `..` в имени;
- `zip_absolute` — абсолютный путь или disk-drive (`/abs/x`, `C:/evil.txt`);
- `zip_bad_name` — пустое имя, символы `<>:"|?*`, управляющие символы, имена
  устройств Windows (`CON`, `NUL`, `COM1`, `LPT1`), путь длиннее 250 символов;
- `zip_symlink` — запись с атрибутом символической ссылки
  (`stat.S_IFMT(info.external_attr >> 16)`);
- `zip_special` — fifo, сокет, блочный/символьный спецфайл;
- `zip_encrypted` — зашифрованная запись (без пароля всё равно не читается);
- `zip_broken` — архив не открывается, обрезан, или содержимое записи читается с
  ошибкой (несовпадение CRC, битый поток сжатия);
- `zip_limit_entries` / `zip_limit_total` / `zip_limit_entry` / `zip_space` /
  `zip_unreadable` / `zip_not_archive` / `zip_io` / `zip_spanned` / `zip_empty`.

Имена в UTF-8 без выставленного флага (бит 11) восстанавливаются из CP437
(`_entry_name`, `container.py:137`): иначе перестают совпадать `fileIdentifier`
LM Studio и имена из манифеста ассетов ChatGPT. Счётчик `name_fixups`.

### 2.4 Метки времени

Для каждой записи `mtime` восстановлен из `ZipInfo.date_time`
(`_restore_mtime`, `container.py:339`, `time.mktime(rec.date_time + (0, 0, -1))` +
`os.utime`), сбой считается и показывается (`utime_failed`).

Это не косметика: правило даты DeepSeek (`adapters\deepseek.py:603-645`) берёт
`created_at` из `st_mtime` файла, если он не раньше `_FILE_MIN_EPOCH = 4.73e8`
(1984-10-30), не «из будущего» и не раньше самого раннего сообщения больше чем на
час. Без восстановления метки у всех бесед из архива сработал бы страж
«служебная метка архива (эпоха zip)» и дата ушла бы из источника. Проверено
кейсом T-Z-14: архив с меткой 2025-06-15 → `created_at = 2025-06-15T05:20Z`;
архив с меткой 1980 → дата из источника + предупреждение «эпоха zip» в
`parse_report`.

### 2.5 Отказ = никакого частичного импорта

`unpack()` (`container.py:205`) делает два прохода: сначала валидация **всех**
записей и лимитов, потом запись. При любом отказе (в том числе на десятой записи)
корень распаковки удаляется целиком (`shutil.rmtree`), временный файл
`<имя>.importer.<pid>.tmp` снимается, и контейнер помечается отклонённым. Так что
«одна беседа импортирована, а вторая нет» из битого архива не получается —
проверено кейсом T-Z-18, где целая беседа из архива с битой записью **не**
импортирована.

### 2.6 Временная область

- имя: `%TEMP%\strawberry-import-<pid>-<uuid8>` (`TEMP_PREFIX`, `container.py:47`);
  внутри — подкаталог по номеру контейнера (`1`, `2`, …);
- при старте `import2.py` удаляет **свои** сироты: каталоги по маске
  `strawberry-import-*` старше 30 минут (`sweep_temp_orphans`, `container.py:110`);
  файлы и чужие папки не трогает;
- `--unpack-dir <путь>` — база области своя; если область оказалась внутри
  `chats` / `attachments` / `backup` — отказ `zip_unpack_inside_archive`
  (иначе импортёр начал бы читать собственную распаковку как вход);
- область удаляется в `finally` — при успехе, при фатальной ошибке и в dry-run;
  `--keep-unpacked` оставляет её и помечает в отчёте `kept: true`.

### 2.7 Что видит оператор

Счётчики: `zips`, `entries`, `bytes`, `rejected`, `zip_in_folder`, `zip_nested`,
`without_chat_files`, `name_fixups`, `utime_failed`, `ZIP_ERRORS`; в
`containers.archives[]` — путь архива, корень распаковки, число записей/файлов/
папок, байты, `sha256` архива, `mtime_restored`, список `nested`.

Коды возврата: отклонённый архив — это проблема входа, то есть **код 1**
(`ZIP_ERRORS` добавлен в список проблемных счётчиков, `import2.py:211`).
Коды 2 (аргументы), 3 (`ASSETS_GUARD`), 4 (фатальное/ошибка записи) не затронуты;
5 остаётся только для `--strict-ambiguous` (C4).

Вход из архива помечен: в списках отчёта — `container: "<архив>!<запись внутри
архива>"`; в архивной беседе — `source_container`, `source_container_entry`,
`source_container_sha256`.

### 2.8 Вложения внутри архива

Пояса поиска байтов LM Studio работают без изменений: для входов из архива
пояс `portable` — это `user-files` внутри области распаковки (в приёмке:
`resolved=3, exact=3, names_restored=3`). Для ChatGPT байты лежат рядом с
`conversations.json`, то есть внутри архива, а указать `--assets-dir` на путь
внутри архива физически нечем, поэтому **для контейнеров** каталог ассетов
подставляется автоматически (`_auto_assets_from_containers`, `engine.py:383`) с
предупреждением в отчёте. Для распакованной папки поведение этапа A не изменилось:
без `--assets-dir` по-прежнему `ASSETS_GUARD` и код 3.

## 3. Как это устроено в коде

`importer_v2\container.py` — новый; он ничего не знает о форматах чатов и про
импортёр в целом (его можно переиспользовать для `strawberry.v1` в C3):

- `sniff_zip()` (`:71`) — «это архив или нет» по первым байтам;
- `archive_sha256()` (`:92`) — хэш архива для отчёта и для поля беседы;
- `new_area()` / `sweep_temp_orphans()` (`:101`, `:110`) — область и сироты;
- `_entry_name()` (`:137`) — имя записи + восстановление CP437;
- `_check_entry()` (`:155`) — вся проверка имени и канонический путь внутри корня;
- `unpack()` (`:205`) — два прохода, лимиты, место, запись, метки, очистка;
- `_write_entry()` (`:308`), `_restore_mtime()` (`:339`).

`importer_v2\engine.py` — распаковка встроена в начало прогона:

- параметры движка `unpack_dir`, `keep_unpacked`, `zip_max_*` (`:138`);
- `_expand_containers()` (`:327`) — вызывается **первой** строкой `_run()`, до
  `preflight_assets`, `lmstudio_roots` и `_collect_inputs`: явный файл-архив →
  распаковка; явный каталог → обход по `.zip` с проверкой сигнатуры; результаты
  добавляются входы как каталоги-основания;
- `_unpack_one()` (`:281`) — один архив: приня́ть/отклонить, «архив без чатов»,
  вложенные ZIP;
- `_zip_taken()` (`:237`) / `_zip_refused()` (`:263`) — счётчики, запись в
  `stats.files` с полем `zip_error`, строка `[ZIP-ОТКАЗ]` в консоли (её видно
  всегда, даже в `--quiet`);
- `_auto_assets_from_containers()` (`:383`), `_container_for()` (`:407`),
  `cleanup_unpack()` (`:417`); `run()` (`:699`) — обёртка
  `try: return self._run(inputs) finally: self.cleanup_unpack()`;
- манифест ассетов ChatGPT как вход → `not_a_chat` с причиной, а не «формат не
  распознан» (`:839`).

Модуль `grouping.py` не создавался: C1 остался в `engine.py`, C2 — в отдельном
`container.py`. Разрешение пользователя: «отдельный модуль не нужен, если
архитектура остаётся понятной и тестируемой» — здесь новый код вынесен в свой
модуль именно потому, что он про транспорт, а не про разбор.

- файлы архива чатов и вложения в двух песочницах идентичны; беседы совпадают по
  `local_id`, `content_hash`, `created_at`, `updated_at`, `source_file_sha256`;

- лимит: при `--zip-max-total-mb 64` архив в 234 МиБ отклонён целиком

- временных областей в `%TEMP%` после прогонов: 0; рабочее хранилище не изменилось.

Время (одинаковая методика — время дочернего процесса целиком): распакованный
вход 4,27 с; ZIP 6,07 с (**накладные расходы +1,80 с** — распаковка 245 МБ в

## 7. Отличия от плана аудита и принятые решения

1. **Имена с недопустимыми в Windows символами отклоняют архив, а не
   «санитизируются»** (`zip_bad_name`). План аудита §2.2 допускал переименование,
   но оно сломало бы сопоставление `fileIdentifier` LM Studio и манифеста имён
   ChatGPT: импортёр ищет байты по имени из JSON. Дешевле отказать и попросить
   пересобрать архив, чем тихо подменить имя.
2. **`source_file_sha256` для беседы из архива — хэш разобранного файла, а не
   архива** (отклонение от буквы контракта C0). Хэш архива — в новом поле
   `source_container_sha256`. Иначе один и тот же экспорт, импортированный
   папкой и архивом, дал бы разные значения в одном и том же поле, и повторный
   импорт перестал бы узнаваться.
3. **`source_file` и `dup_of` внутри архива указывают на путь во временной
   области** (`strawberry-import-<pid>-<uuid8>\1\…`), он не стабилен между
   прогонами: в приёмке 211 из 211 `dup_of` — внутри области. Идентификатором
   беседы по-прежнему остаётся `original_id` + `content_hash`; путь из отчёта
   годится только для чтения «вот копия чего это».
4. **Имя файла нельзя использовать как идентификатор беседы** — подтверждено
   находкой `1787399266109` (разные файлы, одна беседа; см. §8). Для C2 это
   стало аргументом в пользу отдельного поля `container` вместо «разбор имени».
5. **В C2 не вводился классификатор входов `classify_input`** — это C4. Сейчас
   сделано ровно два минимума: определение архива по сигнатуре и счётчик
   `without_chat_files`, чтобы документ-архив не исчезал молча. PDF и MP3 по-прежнему
   дают `read_errors`, а не вежливое «не чат».
6. **`.docx`, `.epub`, `.jar` — настоящие ZIP**: раньше они проходили как
   «формат не распознан», теперь это контейнер без чатов (`without_chat_files` +
   запись `not_a_chat`). Это видимое изменение в отчёте, полезное и
   предусмотренное правилом «ни один вход не исчезает молча».
7. **Манифест имён ассетов ChatGPT как вход** (`conversation_asset_file_names.json`)
   больше не «формат не распознан» с кодом 1 — он служебный файл экспорта,
   помечается `not_a_chat` с причиной. Раньше он давал ложный код 1 при импорте
   официального экспорта целиком.
8. **Отказ от потоковой распаковки «на лету»** (без файла на диске): существующему
   импортёру и поясам вложений нужен реальный путь; файловая система — единственный
   способ сохранить `mtime`, от которого зависит правило даты DeepSeek.
9. **Автоподстановка `--assets-dir` только для контейнеров.** Для распакованной
   папки сохранено поведение этапа A (guard и код 3), чтобы не менять молча то,
   что уже принято.
10. **`ZIP_ERRORS` = код 1**, а не новый код возврата: отклонённый архив —
    проблема входа, а не поломка импортёра.

## 8. Новые находки

- **Легаси-фикстура C0 была неправильной формы.** Генератор писал легаси-сообщения
  парами `[текст, роль]`, а настоящая выгрузка LM Studio —
  `{"messages": [{"role": …, "content": …}]}`, плюс `*.config.chat.json`
  (`name`, `load_params`, `inference_params`) и `*.metadata.chat.json`
  (`identifier`, `name`, `relpath`, `chatConfigurationFilePath`, `stats`,
  `lastUsedModel`, `currentPreset`). После исправления легаси-беседа из ZIP
  распознаётся как легаси (`legacy_imported=1`), а не как «не распознано».
  Фикстуры перегенерированы: 59 файлов / 3 008 482 б (было 3 007 121 б),
  `fixtures_manifest.json` обновлён.
- **Пара `1787399266109`** («история в больнице»): два файла с разными именами —
  одна беседа. Для C3 это основание группы по `conversationId`, а не по имени
  файла; материал оставлен в §9.
- **LM-выгрузка в ZIP**: `user-files` оказывается поясом `portable` внутри
  временной области, все три вложения находятся по имени (`resolved=3 exact=3
  names_restored=3`), дедупликация C1 работает внутри архива
  (`dup_groups=3, dup_group_members=8, dup_members=5, dup_shell_members=2`).
- **Реальная выгрузка = 1016 записей / 245 МБ** — далеко до лимитов C2
  (20 000 записей / 4 ГиБ), так что лимиты по умолчанию не отклоняют обычные
  выгрузки LM Studio; запас места (64 МиБ) тоже проходится свободно.
- Архив без сжатия (`ZIP_STORED`) упаковывается за 1,04 с и распаковывается с
  теми же `mtime`; сжатие на этих данных время экономит незначительно, поэтому
  в приёмке использован STORED.

## 9. Открытые вопросы (передаются в C3/C4)

1. **C3 (`strawberry.v1`)**: основание группы копий — `conversationId`, а не имя
   файла и не `createdAt` (случай `1787399266109`); пакет с маркером формата уже
   не принимается как «просто JSON» — нужен отдельный разбор `manifest.json`.
2. Склейка C1 работает только в пределах одного прогона: раздельные прогоны двух
   половин выгрузки дают `SKIP`, а не `DUP`.
3. Спорные пары `DUP_SUSPECT` не получают второй файл архива — что сохранять при
   противоречии содержимого, решается в C3/C4 вместе с `--strict-ambiguous`.
4. Классификатор `classify_input` (C4): единая причина «не чат» для PDF/MP3/docx
   вместо `read_errors`; сейчас — только минимум C2.
5. Диспетчер разнотипных входов (C4): как выбирать порядок, если в одной папке
   архив, папки и одиночные файлы, и что делать при конфликте имён контейнеров.
6. Новое окно импорта (D): где показать «архив отклонён», «вложенный ZIP не
   распакован», «архив без чатов» и куда деть `--unpack-dir`/`--keep-unpacked`.
7. Что делать с архивом больше лимита: сейчас отказ; варианты — «распакуйте
   вручную и укажите папку» или повышение лимита флагом (флаги уже есть).
8. Многотомные (split) архивы: сейчас отказ `zip_spanned`; поддержка — только по
   явному решению.
9. Гонка R4 (код 4 при конкурентной записи сервера) — вне C2, не трогалась.
