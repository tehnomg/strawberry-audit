### 1.1 Существующий код

* Имя файла в архиве: `store.sanitize_id(oid, source)` → `lmstudio-<createdAt>` (`store.py:25-27`);
  при коллизии — `collision_id` (`store.py:30-31`), применяется в `engine.py:541-548`. Вторая ветка

  тождественно ложна, то есть **столкновение разных `original_id` внутри одного прогона сейчас
  разрешается, а вот три копии одного `original_id` разрешаются как три последовательные записи
  одного файла**.
* Порядок обработки: `run()` (`engine.py:339-340`) идёт по `sorted(path.rglob("*"))`
  (`engine.py:352`), то есть `Migrated` → `Migrated (2)` → `Migrated (3)`; каждая следующая копия
  сравнивается с уже записанным файлом: `decide` (`store.py:153-190`) даёт `UPDATE` при отличии
  `content_hash` и `SKIP` при совпадении; на любую перезапись вызывается `backup_chat`
  (`engine.py:664-665`, `store.py:76-83`).
* Статус `DUP` объявлен в `store.ACTIONS` (`store.py:139-140`) и **не используется нигде** — это и есть
  заложенное место под склейку. `decide()` его не возвращает: `DUP` должен появляться уровнем выше,
  на группировке разобранных бесед внутри прогона.
* Защита этапа B: `model_kept` (`engine.py:605-617`) не даёт копии без сведений о модели понизить
  уже известную модель, поэтому повторные прогоны уже не штормят; но **первый** прогон трёх копий
  по-прежнему делает 104 записи и 104 бэкапа вместо одной.
* Пред-проход легаси (`_lm_covered_ids` 187-210, `_lm_file_class` 211-241, `LEGACY_DUP` 435-448)
  уже решает похожую задачу, но на уровне **файлов** (легаси-копии уже представленных бесед),

   * по каждой группе из >1 копии выбрать одну «лучшую» (п.3), остальные пометить `DUP`
     (счётчик + запись в `stats.chats` с `action: "DUP"`, `note` с путём проигнорированной копии);
   * в основной обход `_run_file` для помеченных копий сразу возвращать `DUP` (без `load_payload`
     и без записи), чтобы не считать вложения и хэши дважды.
   Цена: LM-беседы разбираются дважды (пред-проход + основной) — 543 файла ≈ 58 МБ, приемлемо
   (замер времени обязателен в приёмке C1); либо кэш разбора в памяти по пути файла.
2. **Критерий «это та же беседа».** Склеивать только если `(source, original_id)` совпал **и**
   нормализованный хэш существенного содержимого совпадает (`content_hash` по `title` +
   архивированным сообщениям, **без** `model`; по замеру этого достаточно: 104/105) **или** один
   набор сообщений является префиксом/подмножеством другого (случай пустых оболочек). Если тексты
   расходятся — **не склеивать**: импортировать обе беседы, вторую через `store.collision_id`,
   в отчёт — `dup_suspect` с обоими путями. Это и есть защита от ложной склейки.
3. **Детерминированный выбор «лучшей» копии** (иначе выбор зависит от порядка аргументов и
   повторные прогоны будут расходиться): 1) непустая (есть сообщения; иначе теряется контент, как в
   `1726623283209`); 2) `model_source` ≠ заглушка (`parse_report.model_source` из этапа B:
   `lastUsedModel.identifier`/`preset`/`senderInfo.senderName` важнее заглушки `lmstudio`);
   3) больше суммарный полезный текст; 4) больше сообщений/версий; 5) больше разрешённых байтов
   вложений; 6) свежее mtime; 7) при полном равенстве — минимальный путь относительно корня входа.
   Порядок фиксировать в функции и в `docs\DATA_FORMATS.md`.
4. **Объединение вложений группы.** `clientInputFiles` одинаковы во всех копиях (замер: отличий 0),
   поэтому при выборе копии потеря вложений не грозит; но переносимые `user-files` лежат в разных
   каталогах-поясах (пересечение имён между копиями — 0), поэтому выбранную копию нужно резолвить
   **со всеми поясами** (`lmstudio_roots` это уже делает, `engine.py:129-185`), а не только с
   каталогом-соседом выбранной копии. В `parse_report` выбранной беседы — `merged_copies: N`
   и список путей проигнорированных копий.
5. **Новый счётчик и статус.** `DUP` — в `stats.counts` (статус уже в `store.ACTIONS`,
   `store.py:139-140`) и в `stats.chats` как запись с `action: "DUP"`; отдельный блок
   `stats.groups = {"groups": 333, "multi_copy": 105, "merged": 206, "suspect": 0}`;
   человекочитаемый вывод — `[DUP] lmstudio-<ts>: копия Migrated (2) — та же беседа уже импортирована
   из Migrated`. Код завершения `DUP` **не портит** (как `not_a_chat`/`LEGACY_DUP`,
   `import2.py:159-161`) — развязка №4 (§8).
6. **Что не меняется:** `decide` (`store.py:153-190`), `content_hash`/`observed_hash`
   (`model.py:188-223`) — менять состав хэша нельзя, иначе все 2113 файлов архива перестанут
   совпадать со своими хэшами и дадут волну `SKIP_LOCAL`/`MIGRATE`; `--force`/`SKIP_LOCAL`/
   `CONFLICT`/`ID_MISMATCH` — семантика сохраняется; правило `model_kept` остаётся как страховка
   для одиночных прогонов и другого порядка входов.

### 1.4 Зависимости

C1 не зависит от C2/C3/C4 и даёт наибольший немедленный эффект. C2 и C3 обязаны вызывать ту же
фазу группировки (ZIP-вход даёт те же группы, пакет `strawberry.v1` — одну беседу и в группе быть
не может). Пред-проход легаси (`LEGACY_DUP`, этап B) и склейка копий не должны считать один и тот же
вход дважды — см. §5.2.

### 1.5 Риски

| риск | как снимается |
|---|---|
| ложная склейка двух разных бесед с одним `createdAt` (в LM такое возможно при миграциях) | обязательная сверка существенного хэша; расхождение → две записи через `collision_id` + `dup_suspect` + предупреждение; тест с искусственной парой разных бесед |
| флэппинг между прогонами (сегодня выбрана копия A, завтра копия B → `UPDATE` + бэкап) | детерминированный порядок выбора (§1.3.3), не зависящий от порядка аргументов; тест «переставить порядок входов → тот же результат» |
| потеря контента при выборе «богатой по дате, но пустой» копии | критерий непустоты на первом месте; тест на реальной группе `1726623283209` |
| обход локальных правок пользователя в UI | `decide` вызывается для выбранной копии как раньше → `SKIP_LOCAL`/`CONFLICT` сохраняются; `DUP` не является действием записи |
| двойная трата времени на LM-входы (разбор дважды) | кэш разбора по пути; замер времени прогона в приёмке C1; при деградации — переход на «раз один, потом группировка» (нужна перестройка `_run_file`, риск выше) |
| первый прогон после C1 по реальным `chats` даёт волну `UPDATE` | по замеру §1.2.4 в архиве нет ни одной беседы этой выгрузки → ожидаем 333 `NEW`, а не `UPDATE`; ограничение сохраняется: общий прогон только по решению пользователя |
| удвоение счётчиков (`LEGACY_DUP` + `DUP` на одном входе) | отдельный тест на 106 легаси-семействах + 105 группах: сумма покрывает все 543+318 входов без пересечений |

### 1.6 Тесты C1 (матрица T-C1, песочница в `%TEMP%`, архив не трогать)

1. Три идентичные копии → `NEW 1, DUP 2`; прогон 2 → `SKIP 1, DUP 2`, `backup` пуст.
2. Три копии с разной моделью (заглушка / `lastUsedModel` / `senderInfo`) → выбрана не-заглушка;
   повторный прогон → `SKIP`, 0 бэкапов.
3. Богатая + 2 пустые оболочки (фикстура реальной группы `1726623283209`) → импортируется богатая,
    пустые — `DUP` с причиной «пустая оболочка» (изначально ожидалось `parse_errors`;
    границы C1 №2 и приёмка потребовали `DUP`, реализовано так — см. §12).
4. Две **разные** беседы с одним `createdAt` → импортируется содержательнее, вторая —
    `DUP_SUSPECT` без записи и предупреждением (изначально ожидалась вторая запись через
    `collision_id`; принятое решение C0 №4 «без автоматической склейки» сильнее — см. §12).
5. Копии в трёх каталогах + `user-files` в двух разных поясах → вложения выбранной копии
   разрезолвлены, `resolved` не меньше, чем при импорте каждой копии поодиночке.
6. Перестановка порядка входов (папки в другом порядке, явный список файлов против каталога) →
   идентичные `content_hash` в отчёте и идентичное состояние архива.
7. Легаси-семейства + современные копии (срез `import\chats` + `import\conversations`) →
   `LEGACY_DUP` и `DUP` не пересекаются, покрытие всех входов.
8. Локально изменённый чат (правка в песочном `chats`) + три копии → `SKIP_LOCAL`, `pinned` сохранён,
   записи нет.
9. `--force` с локальной правкой → ровно одна запись и один бэкап (не три).
10. `--dry-run` → `DUP` виден в плане, `chats`/`backup`/`attachments` не изменились.
11. `--source lmstudio` (явный) и без него → одинаковые счётчики.
12. Одна копия из группы (вход — только `Migrated (2)`) → `NEW`; затем полный вход → `SKIP`/`DUP`,
    0 записей (обратный порядок прогонов, как в T-B19).
13. Три копии с расходящимися текстами (искусственно) → предупреждение и `DUP_SUSPECT` у двух
    копий (реализация C1: пишется одна содержательная копия, а не «победа последней»).
14. Вложения выбранной копии из `sidecar_preview` (без байт-файла) → `source_bytes: sidecar_preview`
    сохранится и после склейки.
15. Регресс: T-B1…T-B24 (104 проверки), `test_engine_robustness` (68), `test_deepseek` (135),
    `test_chatgpt_attachments` (99) — все PASS; контрольный прогон на реальном срезе
    `G:\Strawberry\import` в песочнице: прогон 1 `{NEW: 328, DUP: 206…208, UPDATE: 0, parse_errors: 11,
    LEGACY_DUP: 105, not_a_chat: 286}`, прогон 2 `{SKIP: 328, DUP: …, UPDATE: 0}`, файлов в `backup`
    — 0 (было 104); время прогона не хуже, чем 3 с / 2 с до склейки более чем в 1,5 раза.
    **Факт после C1 (см. §12):** групп 106, а не 105 (найдена ещё одна пара копий),
    `DUP` 211 (не 206…208 — пустые оболочки засчитаны `DUP`), `parse_errors` 9 (не 11),
    `UPDATE` 0 и 0 бэкапов, прогон 2 `{SKIP: 328, DUP: 211}`; время прогона лучше базы — 2,55 с вместо
    ~3 с и 1,90 с вместо ~2 с (замер в `%TEMP%\stageC1_time`), остальные условия пункта 15 выполнены
    (регресс 68 + 104 + 135 + 99 без провалов, `backup` пуст).

## 2. C2. ZIP как транспортный формат

### 2.1 Существующий код и фактическое поведение

* Входы: `args.inputs` (`import2.py:29`) → `ImportEngine.run(inputs)` (`engine.py:315`) →
  `_collect_inputs` (`engine.py:346-356`): каталог обходится рекурсивно с фильтром
  `SUPPORTED_SUFFIXES = (".json", ".jsonl", ".md", ".markdown")` (`engine.py:26`); явно указанный
  файл проходит без фильтра. **Фактический дефект текущего поведения:** `.zip` внутри папки в обход
  не попадает и в отчёт не попадает вовсе — молча исчезает (нарушение инварианта 4 в §0.4),
  а явно переданный `.zip` доходит до `load_payload` (`engine.py:47-65`) и даёт `read_errors` с
  JSON-причиной.
* Байты вложений передаются адаптерами в четырёх формах: `_payload` (bytes), `_data_uri`,
  `_local_path`, `_asset_ref` + резолвер (`model.py:45-79`, `attachments.py:127-235`,
  `INTERNAL_ATT_KEYS` — `model.py:120`). **Вывод:** распакованный ZIP достаточно подать как обычный
  каталог — `stage_attachments` и дедуп по `sha256` менять не нужно.
* Готовые образцы «пакет + байты рядом»: ChatGPT — каталог `conversations.json` + `*.dat` +
  манифест имён `conversation_asset_file_names.json` (`engine.py:37`, `_chatgpt_asset_dirs`
  254-274, `preflight_assets` 276-313, чтение манифеста в `adapters\chatgpt.py` ~384-414);
  LM Studio — пояса `user-files` (`engine.py:129-185`) со сверкой имени/размера/`sha256Hex`
  (`adapters\lmstudio.py`, этап B).
* Чтения ZIP в коде StrawBerry нет: `zipfile` встречается только в `restore-attachments.py:42,180`
  (запись резервного архива вложений) и в текстах чатов; в `importer_v2` — ни `zipfile`, ни
  `shutil.unpack_archive`. Веб-окно v1 принимает `.json/.jsonl/.md` (`accept` в `web\index.html:333`),
  эндпоинт загрузки — `POST /api/import/upload` (подробный инвентарь — `experiments\stageC_entry_inventory.md`).
* Клининг сервера удаляет в архиве только `*.importer.*.tmp` старше 1800 с (этап A) — временные
  области распаковки не должны попасть ни в `chats`, ни в `attachments`, ни в `backup`.
* Пути в `stats.files[].file` нестабильны между прогонами (темп), поэтому идентификатором беседы и
  дальше обязан оставаться `original_id` (инвариант 5 в §0.4).

### 2.2 Необходимые изменения (проект)

1. **Новый модуль `importer_v2\container.py`** — реализация проектного «диспетчера входов»
   (`STAGE3_IMPORT_ARCHITECTURE.md` §5) в части контейнеров:
   * `is_zip(path)` по сигнатуре байтов `PK\x03\x04` (пустой `PK\x05\x06` — «ZIP пуст», spanned
     `PK\x07\x08` — отклонить с причиной), независимо от расширения;
   * `classify_input(path)` → `dir | zip | json | jsonl | text | binary_not_a_chat` — сигнатуры
     байтов из STAGE3 §5 (`%PDF`, `ID3`, `ftyp`, `RIFF…WAVE`, `\x89PNG`, `\xff\xd8\xff`, `GIF8`,
     `WEBP`) дают причину «не чат» вместо текущего `undetected 0.00`;
   * `unpack_zip(path, dest, *, max_entries=20000, max_total_bytes=4*1024**3, max_entry_bytes=…)`
     → `UnpackResult{root, entries, bytes_total, errors}`: лимиты проверяются **до** извлечения по
     `ZipInfo.file_size`; защита от zip-slip — отказ при `..`, ведущем `/`, дисковой букве (`C:`),
     симлинках и при недопустимых в Windows символах в именах записей (по образцу
     `safe_user_files_name` из `adapters\lmstudio.py`); имена — UTF-8 по флагу bit 11, иначе CP437
     (флаг `--zip-name-encoding`); вложенные ZIP — не глубже одного уровня, иначе «не поддерживается»
     с причиной.
2. **Куда распаковывать:** только вне рабочего архива. По умолчанию — короткая временная область
   `%TEMP%\strawberry-import-<pid>-<rand>\<n>\` (короткий корень против лимита 260 символов);
   флаги `--unpack-dir` (явный каталог) и `--keep-unpacked` (отладка); удаление в `finally`
   (`import2.py:main`), сироты после Ctrl+C вычищаются по маске `strawberry-import-*` **только в
   `%TEMP%`** (маску клининга архива `*.importer.*.tmp` не менять).
3. **Как распаковка входит в обход:** `run()` (`engine.py:315-344`) заменяет `.zip`-вход на корень
   распаковки **до** `lmstudio_roots(inputs)` и `_collect_inputs(inputs)`. Тогда автоматически:
   * `user-files/` внутри пакета попадает в пояс `portable` (`engine.py:162`) — механика этапа B
     сохраняется без правок резолвера (§5.1);
   * `_chatgpt_asset_dirs` (254-274) находит `.dat` и манифест имён внутри пакета → `--assets-dir`
     можно не передавать;
   * `SUPPORTED_SUFFIXES` трогать не нужно (внутри пакета обычные `.json`).
   Если распаковка отклонена (битый архив, лимиты, zip-slip) — в `stats.files` обязательна строка с
   `entry["zip_error"]` и счётчиком `ZIP_ERRORS` (код завершения 1, не 4), остальные входы обработаны.
4. **Отчёт и план:** `entry["container"] = "<путь.zip>!<внутренний путь>"` (видно, откуда беседа, при
   этом идентификатором остаётся `original_id`), `stats.containers = {"zips": [{"path", "entries",
   "bytes", "root", "kept"}]}`; распаковка выполняется и в `--dry-run` (иначе план врёт про вложения),
   но помечается в отчёте.
5. **Единый код возврата `ASSETS_GUARD`:** матрица STAGE3 (кейс 3) ожидает «rc=4 (или 2)», фактически
   после этапа A — **3** (`import2.py:165-166`). Зафиксировать 3 в документации и поправить матрицу
   (развязка №3 в §8).
6. **Инварианты приёмки из `STAGE2_TECH_SPEC.md` §6-§7**, применимые к распаковке: `PK\x03\x04` как
   признак; в пакете export-v1.1 ровно один JSON чата верхнего уровня (2+ → отказ пакета с причиной, а
   не импорт первого попавшегося); `attachments/` не глубже одного уровня; `..`, абсолютные пути и
   симлинки → отказ; `sha256`/`size` из манифеста сверяются импортёром по фактическим байтам;
   `--dry-run` ничего не создаёт; повторный прогон → `SKIP`.
7. **Две тонкости распаковки, о которых нельзя забыть:** (1) **`mtime` извлечённых записей нужно
   проставлять** из `ZipInfo.date_time`, иначе правило даты DeepSeek (`adapters\deepseek.py:603-644`
   берёт `st_mtime`, со «стражей zip-эпохи» 59-61 и 628-635) получит время распаковки и даты бесед
   уедут; (2) `source_file_sha256 = ctx.file_sha256()` (`engine.py:697-698`, `adapters\base.py:37-42`)
   считает хэш входного файла по пути — при подаче байт через `_payload` без файла это поле
   потеряется. Резолверы (`chatgpt.py:400-412`, `lmstudio.py:160-260`) возвращают `Path`, поэтому
   «читать байты прямо из архива» возможно только через `_payload` (целиком в память,
   `attachments.py:217-223`). Отсюда выбор в пользу распаковки на диск: сохраняются `mtime`,
   `file_sha256` и совместимость с `preflight_assets` (276-313), который видит только диск.

### 2.3 Зависимости

C3 обязан работать на распакованном корне (C2 → C3). C4 вызывает `classify_input`/`unpack_zip` как
часть плана. Настоящие пакеты появятся только после шага 1 форка ACE (экспорт в ZIP), но C2 полностью
тестируется самодельными ZIP-фикстурами и реальными выгрузками, упакованными вручную
(`import\conversations` + `user-files` в один архив). Вызовы `import2.py` из BAT и сервера не меняются
(новых обязательных аргументов не появляется).

### 2.4 Риски

| риск | как снимается |
|---|---|
| zip-slip: запись за пределы временной области (`..\..\`, `C:\`, `/etc`) | проверка каждой записи до извлечения + каноническая проверка пути после; отказ с `zip_error`, архив не тронут |
| место и время распаковки (LM `user-files` — 178 МБ в выгрузке и 239 МБ локально, чат по контракту ≤100 МБ) | лимиты по числу записей и суммарному размеру до извлечения; замер скорости на реальном ZIP в приёмке C2; при превышении — понятная ошибка и код 1 |
| имена записей, недопустимые в Windows (`:`, `?`, `*`, `<>`, `|`), и UTF-8/CP437 | санитайзер имён с сохранением оригинального имени в `parse_report` (как этап B вернул `originalName`), флаг кодировки |
| «исчезновение» входов при отказе распаковки | обязательная строка в `stats.files` + `ZIP_ERRORS` + код 1, остальные входы обработаны |
| темп остаётся после Ctrl+C / падения процесса | уникальный корень по pid+rand, удаление в `finally`, клининг сирот по маске в `%TEMP%` |
| один и тот же чат пришёл и ZIP-ом, и распакованной папкой | группы и `DUP` (§1) работают одинаково: одинаковый `original_id` → один файл, вторая позиция → `DUP` |
| длинные пути (>260) в глубоких архивах | короткий корень темпа + отказ записи с причиной, а не падение |
| ZIP внутри ZIP и мусор (`__MACOSX`, `.DS_Store`) | глубина 1; нечитаемые/неподдерживаемые записи идут в группу «не поддерживается» с причиной |

### 2.5 Тесты C2 (матрица T-Z)

1. `PK\x03\x04` без расширения `.zip` → распознан как ZIP; `.zip` с текстом внутри → не ZIP, обычная
   классификация.
2. zip-slip: `..\evil.json`, `/abs.json`, `C:\x.json`, симлинк → отказ, `zip_error`, архив не изменён.
3. Лимиты: 20001 запись; суммарный размер больше лимита; одна запись больше лимита → `ZIP_ERRORS`,
   код 1, другие входы обработаны.
4. Битый архив (усечённый, не-ZIP с расширением `.zip`, пустой `PK\x05\x06`) → понятная причина,
   остальные входы обработаны, отчёт есть.
5. Пакет с двумя JSON чата верхнего уровня → отказ пакета с причиной (не «импорт первого»).
6. Имена: кириллица в UTF-8; CP437; имя с `:` → санитайзер, `originalName` в `parse_report`.
7. LM-пакет (`*.conversation.json` + `user-files/` + sidecar'ы) внутри ZIP → пояс `portable` = путь
   внутри темпа, `resolved > 0`, `staged > 0`, `names_restored` работает (регресс этапа B).
8. ChatGPT-пакет (`conversations.json` + `*.dat` + манифест имён) внутри ZIP → вложения перенесены
   без явного `--assets-dir`; `ASSETS_GUARD` (код 3) проверяется на недоступном `--assets-dir`.
9. Тот же ZIP дважды → второй прогон: все `SKIP`/`DUP`, `staged: 0`, `reused > 0`, 0 файлов в
   `backup`, 0 новых файлов в `attachments`.
10. Смешанный вход: ZIP + папка + одиночные `.json`/`.md` + `PDF`/`MP3`/`.docx` → каждая позиция в
    одной из трёх групп отчёта, ни одна не исчезла.
11. `--dry-run` с ZIP: счётчики как в реальном прогоне, `chats`/`attachments`/`backup` не изменились,
    темп удалён (кроме `--keep-unpacked`).
12. Сироты в `%TEMP%` старше порога удаляются, файлы другого происхождения не тронуты.
13. Тот же чат из ZIP и из распакованной папки в одном прогоне → один файл чата, `DUP` со ссылкой на
    контейнер.
14. Замер: время распаковки и прогона для реального среза `import\conversations` + `user-files`,
    упакованных в ZIP (числа фиксируются в отчёте подэтапа как базовые).

### 3.3 Зависимости

C2 обязателен (адаптер работает на распакованном корне). Развязки №1 (маркер формата) и №2 (состав
`manifest.json`: обязательные `sha256` и `size` на файл) блокируют полный контроль целостности.
Шаг 1 форка ACE (сам экспорт и добавление `conversationId`) — источник настоящих пакетов: C3
тестируется фикстурами по контракту и может быть принят до готовности расширения, но полный прогон
на настоящих пакетах возможен только после шага 1. C1 на пакет не влияет (одна беседа на пакет),
но два пакета одной беседы без `conversationId` дают два разных `original_id` → два файла архива
(см. риск).

### 3.5 Тесты C3 (матрица T-S)

1. Пакет с 3 вложениями `available` + байтами → `staged 3`, `available` в архиве, имена и mime сохранены.
2. Вложение `no_download_url`/`size_limit`/`cdn_link_only` без байтов → `missing` с причиной, чат
   импортирован, предупреждение; «available без байтов» так же.
3. Подменённый байт (несовпадение `sha256` из манифеста) → вложение не `available`, `sha_mismatch`;
   при отсутствии `sha256` в манифесте — только сверка размера (как 10 sidecar'ов этапа B).
4. `parentId`/`nodeId` + `export.activeLeaf` → та же активная ветка, что в источнике; сообщения вне
   активной ветки видны в `branches.nodes_outside_active`.
5. Сообщение с пустым `content` и вложением → сохранилось (не отброшено).
6. Пакет без маркера формата → что выбрано (`browser.export-v1` 0.9 или `strawberry.v1` 0.75) и что
   показано в плане; с маркером — `strawberry.v1` 0.97.
7. Уверенности всех 8 существующих форматов не изменились (регресс по фикстурам реальных экспортов).
8. Два пакета одной беседы (разные `uuid` в именах) → один файл чата при наличии `conversationId`,
   предупреждение о дубликате при его отсутствии.
9. Пакет беседы, уже импортированной из официального экспорта ChatGPT (`chatgpt-<url-id>`) →
   `SKIP`/`UPDATE`, а не `NEW`.
10. `--source strawberry` (алиас) и автоопределение → одинаковый результат; `time_confidence: source`.
11. Повторный прогон того же пакета → `SKIP`, 0 бэкапов, `reused` по вложениям.
12. Регресс тестов форка (`node --test tests/*.test.mjs`) не затронут; регресс A/B (406 проверок) чист.

## 5. C5. Взаимодействие механизмов этапа C с уже реализованным этапом B

### 5.1 Пояса `user-files` и ZIP

`lmstudio_roots(inputs)` (`engine.py:129-185`) строит пояса `portable` = `<каталог входа>\user-files`
и `neighbor` = `<родитель каталога входа>\user-files`; для входного **файла** используется его
каталог и каталог родителя (149-164). Отсюда обязательное правило C2: ZIP передавать движку как
**корень распаковки**, а не как файл — иначе `portable` укажет рядом с `.zip` (обычно его там нет), и
58 записей вложений уйдут в `not_found`/`no_user_files_root` с предупреждением `_lm_warnings`
(376-408). Приоритет поясов (явный флаг → переносимая → соседняя → локальная) и переопределение
локального пояса через `LMSTUDIO_FILES_DIR` на этапе C не меняются; явный `--lmstudio-files-dir` по
прежнему старше содержимого ZIP (решение пользователя этапа B). Проверка — тест T-Z7.

### 5.2 Пред-проход легаси (`LEGACY_DUP`) и новая склейка копий

`_lm_covered_ids` (187-210) собирает `createdAt` современных бесед **среди всех входов прогона**, а
`_lm_file_class` (211-241) на этом основании относит легаси-файлы `<id>.chat.json` к
`legacy_covered` и даёт `LEGACY_DUP` (435-448). При введении группировки копий `covered` обязан
строиться по всем современным входам, а не только по «выбранным» копиям: иначе легаси-копия беседы,
которую «выбрали из другой копии», станет непокрытой и будет импортирована повторно — появится
второй файл той же беседы. Разделение уровней фиксируется тестом T-C1-7: 106 легаси-семейств +
105 групп копий + 228 одиночных бесед, сумма покрытых входов = 543 + 318 без пересечений,
`LEGACY_DUP` и `DUP` не считают один вход дважды.

### 5.3 Правило «не понижать известную модель» (`model_kept`) и выбор копии

Правило (`engine.py:605-617`) и порядок вычислений (`updated_eff` → `kept_model` → `content_hash` /
`observed_hash`, строки 601-620) менять нельзя: на нём держится отсутствие UPDATE-шторма при
повторных прогонах. После C1 выбор копии с настоящим `model_source` (§1.3.3) означает, что правило
срабатывает реже, но оно обязано остаться как страховка для прогонов по одной копии и для другого
порядка входов. Опора выбора копии на `parse_report.model_source` (добавлен на этапе B) уже есть;
при добавлении новых полей (`merged_copies`, `dup_suspect`, `groups`) их нужно внести в whitelist
`_trim_report` (`engine.py:729-745`), иначе они исчезнут из отчёта — это механический, уже известный
по этапам A/B дефект фильтрации отчёта.

### 5.4 Счётчики LM-блока отчёта

`_merge_lm_stats` (358-374), `_lm_warnings` (376-408), `report.summarize` (69) и `summary_text`
(101-117) печатают `records/resolved/exact/sidecar_preview/size_mismatch/sha_mismatch/name_case_only/
not_found/identifier_not_a_file_name/no_user_files_root/names_restored/legacy_imported/
legacy_covered/sidecars_skipped`. После C1 проигнорированные копии не разбираются и не дают своих
записей вложений, поэтому суммарный `records` может уменьшиться на число записей в отброшенных
копиях. Чтобы приёмка этапа B (контрольные `records: 58, staged: 57, reused: 1, missing: 0`) осталась
понятной: (1) семантика `records` — «записи вложений импортируемых бесед»; (2) рядом добавляется
справочный `records_in_skipped_copies`; (3) `resolve_errors` выбранных копий сохраняется как раньше.

### 5.5 Идемпотентность, бэкапы и коды завершения

Инвариант 1 (§0.4) выполняется после этапа B и обязан сохраниться: прогон 2 = `{SKIP: 536}`,

## 7. Сводка главных рисков этапа C (топ-7)

1. **Изменение состава хэша** (`content_hash` в `model.py:188-207`) ради «решения» UPDATE-шторма
   рассогласует хэши всех 2113 файлов архива и вызовет волну `SKIP_LOCAL`/`MIGRATE`. Решение — на
   уровне группировки (`DUP`), хэш не трогать.
2. **Ложная склейка** разных бесед под одним `createdAt` — в реальной выгрузке таких случаев 0, но
   правило «только идентичное/префиксное содержимое» обязательно, иначе потеря беседы необратима
