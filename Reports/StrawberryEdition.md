# StrawberryEdition — форк расширения ACE под архив StrawBerry

**Путь:** `Workspace\StrawberryEdition\`
**Даты:** начато 20.11.2026 (~22:05, +05:00). **Этап 1 (аудит) и этап 2 (спецификация) завершены; в этапе 3 выполнены шаг 0 (копия форка, сборка, проверка изоляции) и часть шага 1а (замеры). Реализация шага 1 не начиналась — правок в коде форка нет, нужен доступ к живой сессии ChatGPT.**
**Задание:** последовательность работ «Strawberry Edition» (5 этапов): расширение-экспортёр ACE → локальный архив чатов StrawBerry (`G:\Strawberry`).

## Цель

Сделать отдельную версию браузерного расширения AI Chat Exporter (ACE, `github.com/Covai-Labs/ace`), которая экспортирует чаты (первым — ChatGPT) в формате, который архив StrawBerry принимает **со всеми вложениями** (картинки и файлы оригинальными байтами), не трогая оригинальный ACE.

## Решения пользователя (20.11.2026, зафиксированы в спецификации)

1. **Доставка:** один ZIP-архив — JSON чата + папка `attachments` с реальными файлами; импорт через существующий проверенный `import2.py`. Прямую отправку из расширения на локальный сервер пока не реализовывать.
2. **Формат:** отдельный Strawberry v1.1; стандартный формат ACE не менять, совместимость с текущим импортом ACE не ломать; сохранять `message_id` и `parent_id` активной цепочки; полноценный экспорт всех веток — вне объёма работ.
3. **Рассуждения модели:** в тексте с маркерами, как в существующем ACE; отдельное поле `reasoning` не вводить.
4. **Ограничения:** не считать сохранением вложения простое сохранение URL или base64 в тексте; не обещать сохранение ресурсов, доступность которых не подтверждена экспериментально; исходники ACE и StrawBerry, а также рабочую установку StrawBerry не менять.
5. **Транспорт ZIP:** `import2.py` сам принимает ZIP транспортного формата, распаковывает его во временную рабочую область, обрабатывает JSON и вложения и импортирует в существующее штатное хранилище StrawBerry (`chats\`, `attachments\<имя_чата>\`, штатные имена и расширения, `url`, `status:"available"`, дедуп существующими механизмами). После импорта ZIP не нужен; структуру хранения под транспорт не менять, параллельную систему вложений не создавать.
6. **Проверка HTML-экспорта (21.11.2026):** наличие изображения внутри HTML не считать доказательством сохранения оригинального файла; оригиналом считается только файл в `attachments\` с подтверждённым SHA256.

1. StrawBerry **уже** принимает формат ACE: адаптер `G:\Strawberry\importer_v2\adapters\browser_v1.py` (`browser.export-v1`), по DeepSeek такой экспорт стоит в проде.

## Ключевые решения этапа 2 (детали — в `STAGE2_TECH_SPEC.md`)

- **Пакет:** `chat.json` + `attachments/<attachmentId>.dat` (реальные байты) + `attachments/conversation_asset_file_names.json` (имя → оригинал) + `manifest.json`. Имена файлов в пакете — ASCII по идентификатору ассета, имена оригинов — только в манифесте.

- **Правки StrawBerry минимальны:** новый адаптер `strawberry.v1` (уверенность детекта ≥0.95 против 0.9 у `browser.export-v1`) + поддержка `.zip` в `import2.py`/`engine.py` + авто-`assets_dir` из пакета. Путь v1 и UI-импорт не трогаются.

## Что дали шаг 0 и часть шага 1а (замеры 20–21.11.2026)

1. **Форк готовится к работе:** `ace-fork` собирается на установленном Node 24.16 (переносимый Node 26 не понадобился), собранная копия реально устанавливается и запускается во временном профиле Edge; рабочая установка StrawBerry не тронута (0 изменённых файлов), `import2.py` не изменялся.
2. **Изоляция форка требует правок (подтверждено замером):** id unpacked-расширений не конфликтуют (`key` в манифесте нет → id из пути), но две одинаковые копии в одном профиле получили `disable_reasons:[16777216]` и не запустились — причиной стали одинаковые `commands` (`Alt+Shift+C/D/P`) и одинаковое имя; для Firefox нужно менять жёстко прописанный gecko id; помощник страницы перехватывает чужие сообщения (общий `source`, глобальный флаг, общий id инжектируемого скрипта).
3. **HTML-экспорт ACE исследован на реальных файлах:** картинки в нём — base64 data URI, байт в байт совпадающие с оригиналами из архива (SHA256 и размер), санитайзер их не трогает, масштаб 60 картинок → 59 МБ HTML за 1,1 с без потерь. Но: байтов документов в HTML нет вообще, имён файлов у картинок нет, идентификаторов ассетов нет, недоступные ссылки остаются внешними, а полученная по внешнему URL картинка может быть уменьшенным рендишем (замер: `?w=400` → 28 359 б против `?w=1600` → 298 542 б, разные SHA256). Вывод: HTML годится только как аварийный канал для изображений с обязательной SHA256-сверкой, основным источником остаётся `asset id → files/download → attachments\`.
4. **Эндпоинты без авторизации:** `conversation` и `files/download` — 401 (нужна сессия), маршрута `files/<id>/metadata` не существует (404).
5. **Данные архива для будущих замеров:** 102 чата ChatGPT, 17 с вложениями, 53 записи с `source_id` вида `file_0000…`; типов: jpeg 20, md 10, txt 9, py 9, json/pdf/webp/js по 1. В `attachments\` нет ни одного `.pdf`/`.docx`/`.xlsx`, хотя запись о PDF на 10 249 512 байт есть и она в статусе `missing` — байты не донёс даже путь официального пакета экспорта. Публичных `/share/`-ссылок и CDN-ссылок в архиве нет.

## Три уровня мультимедиа: что StrawBerry может хранить, импортировать, показывать (замер 21.11.2026)

Отдельная проверка по требованию пользователя: не менять архитектуру, а установить, **способна ли существующая модель хранения сохранить видео, аудио, документ и произвольный бинарный файл без потерь**. Числа, замеры и ссылки на строки — в `STAGE3_MEDIA_TYPES.md`.

1. **Хранение — способно, правок не нужно.** В записях вложений реально лежат `name` (в т. ч. кириллица), `mime`, `size`, `sha256`, `status`, `url`, `format_hint`, `source_id`; схема не замкнута на фиксированный набор полей — `archive_attachment` пишет всё неслужебное, поэтому дополнительные поля доживают до архива. В архиве уже есть не-картинки: pdf 20 записей, `video/mp4`, `audio/x-m4a`, docx, и **произвольный `coffee_t2va.ir` со статусом `available`, без `mime`** — то есть модель вложений действительно расширяемая, а не список заранее известных расширений.
2. **Импорт — принимает любые байты.** Сквозной прогон штатного `import2.py` в песочнице: mp4 (ftyp), m4a, docx (PK), произвольный `.ir`, jpg — **все 5 файлов совпали с исходными по SHA256**, легли в `attachments\<chat_id>\<sha256>.<ext>`, получили `url` и `status:"available"`; второй прогон того же пакета даёт `SKIP` + `reused 5` (идемпотентность). Отдельно 17 типов × 3 способа доставки байтов (`_payload`, `_local_path`, `_asset_ref`+манифест) — **51/51 совпали байт в байт**. Сигнатуры байтов импортёр знает только для jpg/png/gif/webp/pdf (для них он сам исправляет ложный MIME и сохраняет `declared_mime`), для видео/аудио/офиса/неизвестных форматов — доверяет расширению из `name`.
3. **Единственный настоящий пробел — интерфейс.** Элементов `<video>`/`<audio>` в `web\` нет вообще, видео и аудио только скачиваются; вложения ассистентских сообщений не рисуются вовсе (ветка `msgEl` для `role === "user"`, app.js 821-889, против ассистента 890-905) — а у ChatGPT сгенерированные картинки и файлы относятся именно к сообщениям ассистента; корзина `images` рисуется тегом `<img>`, поэтому не-image медиа обязаны попадать в `files`. Сервер при этом раздаёт всё: 5 типов картинок `inline`, 28 известных типов с точным Content-Type (включая `.mp4 .webm .mov .mp3 .wav .ogg .pdf .zip .gz`), остальное `application/octet-stream` + `attachment`. Это косметика, а не потеря данных, и она не блокирует универсальный экспорт.
4. **Чего не хватает в транспортном смысле:** в `import2.py`/`engine.py` нет поддержки `.zip` (`SUPPORTED_SUFFIXES` — только `.json/.jsonl/.md/.markdown`), а адаптер `browser.export-v1` (формат ACE) вложения не читает вовсе — **в 2113 чатах архива нет ни одного чата с вложениями, импортированного браузерными адаптерами** (вложения есть только у `qwen.package` 450, `deepseek.package` 326, `lmstudio.json` 49, `chatgpt.package` 17, `claude.package` 2). Байты для Qwen не скачиваются нигде: 1963/1963 записей в статусе `remote`, сетевого кода в `importer_v2` нет. Подтверждает транспортную модель: байты привозит пакет.
5. **Правила для нормализатора и пакета (фиксация, не реализация):** ровно две корзины `images`/`files`; всё не-image медиа — в `files`; `kind` для совместимости `image`/`file`, семантика типа — в отдельном поле; `name` обязано нести настоящее расширение, `format_hint` — страховка (иначе файл станет `.bin`/`.dat`: байты целые, но Content-Type деградирует); тип для mp4/mp3/m4a/docx/xlsx экспортёр определяет по первым байтам сам; в манифесте пакета — `sha256` и `size` каждого файла, которые импортёр пересчитывает штатно.

## Подэтап C2 выполнен: ZIP как транспортный контейнер (21.11.2026 19:00)

Разрешение пользователя: «теперь занимаемся исключительно ZIP как транспортным контейнером»,
с ограничением «если ZIP превышает лимиты или содержит опасную запись, отклоняется весь архив.
Никакого частичного импорта его содержимого». Отчёт — `STAGE_C2_ZIP_TRANSPORT.md`; раздел 13 аудита
`STAGE_C_AUDIT_SPEC.md` фиксирует отклонения от плана.

**Как это работает.** Архив определяется по сигнатуре, а не по расширению: `PK\x03\x04` — архив
(даже без `.zip`, даже `.docx`), `PK\x05\x06` — пустой (отказ `zip_empty`), `PK\x07\x08` —
многотомный (отказ `zip_spanned`), файл с расширением `.zip` и другой сигнатурой — обычный вход.
Распаковка идёт **до** всего остального (`_expand_containers`, `engine.py:327`, первой строкой `_run`):
явный файл-архив и архивы, найденные обходом выбранной папки (`zip_in_folder`), раскладываются в
`%TEMP%\strawberry-import-<pid>-<uuid8>`, и эти каталоги становятся основаниями поиска поясов
вложений. Лимиты: 20 000 записей, 4 ГиБ суммарно, 512 МиБ на запись, свободное место с запасом
64 МиБ; флаги `--zip-max-entries`, `--zip-max-total-mb`, `--zip-max-entry-mb`, `--unpack-dir`,
`--keep-unpacked`. Проверка двухпроходная: сначала все записи и лимиты, потом запись через
`<имя>.importer.<pid>.tmp`; при любой ошибке распакованное удаляется целиком — частичного импорта
не бывает (проверено на архиве с испорченным CRC: целая беседа из него не импортирована).
Опасные записи отклоняют архив: `zip_slip`, `zip_traversal`, `zip_absolute` (в том числе `C:/evil.txt`),
`zip_bad_name` (`<>:"|?*`, управляющие, `CON`/`NUL`, путь > 250 символов), `zip_symlink`,
`zip_special`, `zip_encrypted`, `zip_broken`, `zip_space`, `zip_unpack_inside_archive`. Имена в UTF-8
без флага UTF-8 восстанавливаются из CP437 (`name_fixups`), `mtime` — из `ZipInfo.date_time`
(обязательно: правило даты DeepSeek берёт `created_at` из `st_mtime`, а «эпоху zip» отбраковывает
страж `adapters\deepseek.py:628`). Вложенный ZIP автоматически не распаковывается (`zip_nested`),
архив без чатов (`.docx`, `.epub`, `.jar`) помечается `without_chat_files` + `not_a_chat`, чтобы вход
не исчезал молча. Отклонённый архив — счётчик `ZIP_ERRORS` → код возврата **1**.

разные значения в одном поле. Пути `source_file` и `dup_of` у входов из архива лежат внутри временной
