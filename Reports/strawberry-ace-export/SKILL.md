## ChatGPT: где брать данные и вложения

- Каскад в `chatgpt.js: parse()`: SSR-дамп (`/share/…`, картинок нет) → внутренний API (основной) → DOM с прокруткой → iframe Deep Research.
- API: токен из `#client-bootstrap` (`session.accessToken`), id из URL `/c/<uuid>`; `GET https://chatgpt.com/backend-api/conversation/<convId>` с `Authorization: Bearer` + `oai-device-id` из cookie `oai-did`; ответ приходит `postMessage`-ом (таймауты 45 с / 60 с с картинками, кэш 20 с).
- Ответ бывает двух форм: старый `mapping` (дерево узлов) и новый `messages` (плоский список) — обе поддержаны.
- **Ветки:** `linearize()` идёт от активного листа (`resolveActiveLeafNode` по DOM-атрибутам `data-message-id`/`data-turn-id`) вверх по `parent`; соседние `children` теряются без счётчиков.
- **Картинки (подтверждено кодом):** собираются `content.parts[].content_type == "image_asset_pointer"` → `fileId = asset_pointer.split("://")[1]` (работает для `file-service://…` и `sediment://…`) → `GET /backend-api/files/download/<fileId>` → `download_url` → base64 data-URL. Только при наличии токена.
- **Не-картинки:** только имена (`msg.metadata.attachments` → `**File:** имя`; в DOM-ветке регулярки на `.tex/.txt/.md/.pdf/.doc` — `docx` не матчится, класс `[a-zA-Z0-9_-]` не содержит `x`). Байтов не запрашивается ни для чего, кроме картинок.
- Не подтверждено (замер на этапе 4, не «авось заработает»): работает ли `files/download` для PDF/DOCX/XLSX; доступен ли `backend-api/files/{id}/metadata`; живы ли ассеты сгенерированных картинок на `/share/`; сколько живут ссылки `images.openai.com`/`oaistatic`.

## Схема архива (то, что должен выдать экспортёр)

- Файл чата: `id` (== имя файла, `[A-Za-z0-9-_.]` ≤200; импортированные — `{source}-{original_id}`), `title`, `source`, `source_kind`, `original_id`, `model`, `messages[]`, `created_at/updated_at/imported_at/source_created_at/source_updated_at`, `time_confidence`, `source_message_count`, `source_content_hash(+_version=3)`, `source_observed_hash`, `branches`, `parse_report`, `importer_version`, `source_file(+sha256)`.
- Сообщение: `role, text, time, time_precision, message_id, parent_id, reasoning, tools[], images[], files[], model, edited`. Роли фактически `user`/`assistant`. Числовые времена внутри архива — **миллисекунды**, в выгрузках ChatGPT/Qwen — секунды (ошибка ×1000).
- Вложение: `kind, source, source_id, name, mime, size, status ("available"|"remote"|"missing"), url, source_url/source_ref, format_hint, sha256, width, height, declared_mime, extracted_text`; `url` только после реального сохранения байтов; формат на диске — по сигнатуре байтов.
- Сортировка ленты: «по обсуждению» = `source_updated_at → created_at → imported_at`; `mtime` файла не участвует (но правило воли пользователя: дата импортируемого чата = mtime файла выгрузки, с guard'ом на zip-метку 1980).
- Фронтенд: картинки/файлы рисуются по `url` из `images[]/files[]` (без `url` — «файл не перенесён»); markdown-картинки из текста — только хосты из `IMAGE_CDN_HOSTS = {images.openai.com, files.deepseeksvc.com}` (`web\app.js:1155`); 4 МБ/4 картинки — про отправку в модель, не про импорт.
- Веток в UI нет: в архив попадает одна активная цепочка, альт-ветки только посчитаны в `branches`/`parse_report`. «Branch from here» = новый чат.

## Типовые подводные камни

- Не терять молча: не скачали байты → `status:"remote"/"missing"` + причина (так уже делают адаптеры StrawBerry).
- Дубли: разные `original_id` → разные файлы; один UUID на разные чаты → суффикс `_{md5[:6]}`; чат, изменённый вручную, без `--force` пропускается (хэш v3 включает `time, message_id, parent_id`).
- Не-ASCII `original_id` → `_`; в `attachments\<id>` нет подкаталогов, имя файла не может начинаться с `.` и содержать `..`.
- Base64 в JSON раздувает файл (~+33%), StrawBerry при импорте превращает его в файлы и дедуплицирует по sha256; лимита тела запроса в `/api/import/upload` нет (читает в память).
- После импорта — прогнать `card-builder.bat`, иначе чат не участвует в тегированном поиске.
- Правки в `chatgpt_helper.js` (инжект в page-world) — место, чаще всего ломающееся при изменениях ChatGPT; трогать точечно.
- Форк обязан называться иначе и иметь отдельный id/иконки, чтобы не конфликтовать с установленным ACE; оригинальный ACE в репозитории не правится.

## Три уровня мультимедиа: что StrawBerry хранит, импортирует и показывает (замерено 21.11.2026)

Замеры на реальных данных (`probe\scan_att_model.py`, `probe\scan_by_source.py`) и на песочнице (`experiments\run_att_types_experiment.py`, `experiments\run_engine_sandbox.py`, `experiments\kind_probe\`); полный разбор — `StrawberryEdition\STAGE3_MEDIA_TYPES.md`. Рабочие `chats\` и `attachments\` не изменялись.

**Хранение — способно, правок не требует.** Схема не замкнута: `model.py:134-140 archive_attachment` пишет в архив всё неслужебное и непустое, поэтому в реальных записях живут `token_usage` (1421), `file_inserted_at` (1421), `file_identifier` (192), `library_file_id` (32), `extracted_text`, `unrecoverable_*`. **Импорт — принимает любые байты.** Сквозной прогон настоящего `import2.py` в песочнице (mp4 ftyp 400 КБ, m4a, docx PK, произвольный `.ir`, jpg): `staged 5, missing 0, unique 5`, каждый файл **совпал с исходным по SHA256**, лег в `attachments\<chat_id>\<sha256>.<ext>` с `url` и `status:"available"`; второй прогон → `SKIP`, `reused 5`. 17 типов × 3 доставки (`_payload` / `_local_path` / `_asset_ref`+манифест) → **51/51 байт-в-байт**. **Единственная деградация — имя/расширение, а не байты.** Приоритет расширения (`_ext_for`, `attachments.py:102-113`): расширение из `name` → таблица по MIME → `format_hint`/имя файла-источника → `bin`; файл без расширения в имени, переданный как `<id>.dat`, лег как `<sha256>.dat`. ## Дедупликация копий LM Studio (реализовано, подэтап C1, 21.11.2026)

Главный документ — `StrawberryEdition\STAGE_C1_LM_DEDUP.md`; отклонения от плана аудита — его раздел 7
и раздел 12 `STAGE_C_AUDIT_SPEC.md`; скрипт приёмки на реальном срезе —
`StrawberryEdition\experiments\run_stageC1_verify.py` (лог `experiments\stageC1_acceptance_run.txt`).

**Механика (что делать, если придётся править дальше).** План групп строится **до** обхода входов:
`ImportEngine._lm_dup_plan` (`engine.py:219-301`) читает каждый `*.conversation.json` входа, берёт
`createdAt` и отпечаток `substance_of`, помечает наличие известной модели (`lastUsedModel.identifier` /
`.title` / `.key`) и складывает группы ≥2 участников в `self.lm_plan` и индекс
`self._lm_dup_by_path` (путь → участник, победитель, `createdAt`). Участники сортируются по `str(path)`
до выбора победителя, иначе результат зависел бы от того, передан вход каталогом (обход сортируется)
или списком файлов (не сортируется) — этот дефект был найден и исправлен тестом T-C1-6. Победитель:
`max` по `(число сообщений, число записей вложений, есть известная модель, путь)`. Действие для
неосновной копии определяет единственная функция `_dup_action` (`engine.py:303-319`).

**Три ловушки, которые уже сработали при реализации:**
1. LM-адаптер отвергает пустую беседу как `AdapterError` с кодом `lmstudio_empty` («LM Studio: 0 бесед
   из 1 ([])»), и файл уходил в `parse_errors`, не доходя до дедупликации. Поэтому решение берётся из
   плана по пути входа (`_lm_dup_for_path`, `engine.py:321-339`) и проверяется в ветке
   `except AdapterError` **до** учёта `parse_errors` (`engine.py:635`).
2. Выбор «первого встречного» понижал модель: если первой по обходу шла копия без `lastUsedModel`,
   настоящая модель терялась (заглушка `"lmstudio"`), несмотря на правило `kept_model` этапа B.
   Отсюда третий признак победителя — известная модель.
3. Флаг «группа с противоречием» нельзя считать по множеству отпечатков: группа «полная копия + пустые
   оболочки» давала ложное предупреждение. `suspect` вычисляется через `_dup_action` по участникам,
   для оболочек есть отдельный счётчик `dup_shell_members`.

**Счётчики (новый блок `lmstudio` в отчёте и в строке `ИТОГ`):** `dup_groups` (число групп ≥2),
`dup_group_members` (все участники), `dup_groups_suspect`, `dup_members`, `dup_suspect_members`,
`dup_shell_members`, а также `covered_families`. Инвариант: `dup_group_members − dup_groups ==
dup_members`. В `stats.chats` копия попадает с полями `action` (`DUP`/`DUP_SUSPECT`), `dup_of` (имя
основного файла архива), `note` (причина), `substance`/`kept_substance` (отпечатки).
`LEGACY_DUP` (легаси-семейства, этап B), `not_a_chat` (sidecar'ы) и `DUP` (копии) — разные уровни,
один вход попадает ровно в один счётчик.

**Что не создаётся для копий:** файл чата, резервная копия, запись в `attachments`. Разбор адаптером
при этом выполняется (сохраняются счётчики поясов вложений этапа B: `records`, `resolved`,
`sidecar_preview` считаются по всем копиям), байты переносятся один раз.

## ZIP как транспорт (реализовано, подэтап C2, 21.11.2026)

Главный документ — `Workspace\StrawberryEdition\STAGE_C2_ZIP_TRANSPORT.md`. Код: новый
`importer_v2\container.py` (346 строк) + встройка в `engine.py` (931 → 1200), `report.py`
(153 → 178), `import2.py` (182 → 220). Тест — `importer_v2\tests\test_zip_transport.py`
(18 кейсов T-Z, 195 проверок).

Как пользоваться:

```
python import2.py G:\lmstudio-export.zip --dry-run        # архив как единственный вход
python import2.py G:\импорт --dry-run                     # архив внутри папки найдётся сам
python import2.py big.zip --zip-max-total-mb 8192 --keep-unpacked
```

Что гарантирует код:

- архив определяется **по сигнатуре**, а не по расширению: `PK\x03\x04` — архив (даже без
  `.zip`, даже `.docx`), `PK\x05\x06` — пустой (отказ), `PK\x07\x08` — многотомный (отказ),
  файл с расширением `.zip` и другой сигнатурой — обычный вход;
- лимиты по умолчанию: **20 000 записей / 4 ГиБ суммарно / 512 МиБ на запись**, плюс проверка
  свободного места (размер + запас 64 МиБ). Флаги: `--zip-max-entries`, `--zip-max-total-mb`,
  `--zip-max-entry-mb`; сама распаковка — `--unpack-dir`, `--keep-unpacked`;
- **отказывает весь архив**, частичного импорта не бывает: сначала проверяются все записи и
  лимиты, потом запись; при любой ошибке (в том числе на десятой записи, при несовпадении CRC)
  распакованное удаляется целиком. Причины отказа — в блоке `containers` отчёта и в строке
  `[ZIP-ОТКАЗ]` (её видно и в `--quiet`);
- опасные записи отклоняют архив: `zip_slip` (выход за корень), `zip_traversal` (`../`),
  `zip_absolute` (`/abs`, `C:/evil.txt`), `zip_bad_name` (`<>:"|?*`, управляющие, `CON`/`NUL`,
  путь > 250 символов), `zip_symlink`, `zip_special` (fifo), `zip_encrypted`, `zip_broken`,
  `zip_spanned`, `zip_empty`, `zip_limit_*`, `zip_space`, `zip_unpack_inside_archive`;
- имена в UTF-8 без флага UTF-8 восстанавливаются из CP437 (`name_fixups`) — иначе разъезжаются
  `fileIdentifier` LM Studio и манифест имён ChatGPT;
- `mtime` восстанавливается из `ZipInfo.date_time` (**обязательно**: правило даты DeepSeek берёт
  `created_at` из `st_mtime` файла, а метка «эпоха zip» (1980) отбраковывается стражем
  `_FILE_MIN_EPOCH = 4.73e8`);
- временная область — `%TEMP%\strawberry-import-<pid>-<uuid8>`, удаляется в `finally` (успех,
  ошибка, dry-run); при старте удаляются сироты по этой маске старше 30 минут; вглубь
  `chats`/`attachments`/`backup` распаковка запрещена;
- счётчики: `zips`, `entries`, `bytes`, `rejected`, `zip_in_folder`, `zip_nested` (вложенный ZIP
  не раскрывается), `without_chat_files` (`.docx`/`.epub`/`.jar` — архив без чатов), `name_fixups`,
  `utime_failed`, **`ZIP_ERRORS` → код возврата 1**;
- идентификация: у входа в отчёте — `container: "<архив>!<запись>"`, у беседы —
  `source_container`, `source_container_entry`, `source_container_sha256`; `source_file_sha256`
  остаётся хэшем **разобранного файла**, чтобы папка и архив давали одинаковые значения;
- вложения из архива работают штатно: пояс `portable` = `user-files` внутри области распаковки;
  для ChatGPT каталог ассетов внутри архива подставляется автоматически (внутри архива
  `--assets-dir` указать нечем), для распакованной папки — по-прежнему `ASSETS_GUARD` и код 3.

Замер на реальном срезе (`experiments\stageC2_acceptance_run.txt`, 21 проверка, 0 провалов):
