## 1. Как рождается запрос к LLM

Один путь, весь сбор промпта — **на стороне браузера**:

1. Отправка сообщения → `streamAnswer()` (`web/app.js:1368`).
2. Тело запроса (`web/app.js:1380–1401`):
   - `model` — только из активного подключения (`Connections.selectedModel`, `app.js:1377`);
   - `messages: await apiMessages()` (`app.js:1382`);
   - `stream: true`;
   - sampling/thinking/reasoning/mcp/vision — через `Providers.requestExtra()` (`app.js:1385–1401`).
3. `prefixMessages` (`app.js:1393`): если первое сообщение — `system`, ставится `1`.
   Комментарий в коде прямо говорит: *«system-инструкция вместе с блоком `<memory>` идут
   первыми и одинаковы во всех диалогах, поэтому их помечаем как префикс (1 сообщение)»*.
   Это значит: **общая префиксная часть кэшируется движком**, и любой текст, который мы
   хотим дёшево держать в контексте, обязан быть внутри этого первого сообщения.
4. Запрос уходит в прокси `/api/proxy/{path}` (`history-server.py:247`, `_do_proxy` 154+).
   Сервер **ничего не добавляет к messages**: он прозрачный (`HOP_BY_HOP`, `app.js`-сборка).

Вывод: единственное место, где можно собрать System Prompt динамически, — `apiMessages()`
в `web/app.js`. Сервер в сборке промпта участия не берёт.

## 2. `apiMessages()` — фактическая сборка сообщений

`web/app.js:1249–1308`. Ровно то, что нужно заданию:

```
1249  async function apiMessages() {
1250    const out = [];
1251    const local = isLocalConn(conn());
1252    const warns = [];
1254    if (memoryEnabled) {
1255      const parts = [];
1257      // 1. System Prompt (глобальный)
1258      if (systemPromptText && systemPromptText.trim()) {
1259        parts.push(systemPromptText.trim());
1260      }
1262      // 2. Memory Profile (текущий)
1263      if (memoryText && memoryText.trim()) {
1264        parts.push(`<memory>\n${memoryText}\n</memory>`);
1265      }
1267      if (parts.length) {
1268        out.push({role: "system", content: parts.join("\n\n---\n\n")});
1272      }
1273    }
1275    for (const m of messages) { ...история, картинки, файлы... }
1307    return out;
```

Три факта, важных для проекта:

- **(Ф1) Одно system-сообщение.** Общий System Prompt и память склеиваются в **одну**
  строку через разделитель `\n\n---\n\n`. Второй `role:"system"` не создаётся.
- **(Ф2) Всё System Prompt живёт под флагом `memoryEnabled`.** При выключенном профиле
  (`Profile: OFF`) в запрос **не уходит ни память, ни общий System Prompt**. Флаг называется
  «профиль», но фактически выключает и системные инструкции.
- **(Ф3) Порядок фиксирован:** сначала общий промпт, потом `<memory>`. Значит раздел,
  добавленный в общий промпт, стоит в тексте **до** памяти пользователя — это уже
  обеспечивает приоритет правил Visual Protocol над памятью (формально порядок не решает,
  но в связке с правилом приоритета §9.2 п.5 — да).

## 3. Откуда берётся общий System Prompt

Клиент:
- `loadSystemPrompt()` — `web/app.js:2146–2154`, `GET api/system-prompt`, кладёт в
  глобальную `systemPromptText` (`app.js:1806`).
- Вызывается **один раз при старте страницы** (`app.js:2807`) и повторно при открытии
  вкладки «System» в окне профилей (`app.js:1987–1992`).
- Правится в том же окне: `system-prompt-textarea` (`app.js:1919`), кнопка
  «Save System Prompt» (`app.js:1921, 2338–2352`) → `POST api/system-prompt`.

Сервер:
- `SYSTEM_PROMPT_FILE = BASE_DIR / "system-prompt.md"` (`history-server.py:122`,
  `BASE_DIR = Path(__file__).parent` — `history-server.py:24`);
- `GET /api/system-prompt` — `124–128`, при отсутствии файла создаёт пустой;
- `POST /api/system-prompt` — `130–140`, атомарная запись через `.tmp` + `replace`.

**(Ф4) Разыменование файлов — находка этой стадии.** На диске:

| файл | размер | что с ним делает код |
|---|---|---|
| `G:\Strawberry\system-prompt.md` | **0 Б** (25.11 00:05) | единственный, который читается сервером и уходит в LLM |
| `G:\Strawberry\общий system-prompt.md` | 8 048 Б | **ни в `.py`, ни в `.js` не упоминается** (проверено grep по всему дереву) |

То есть содержимое `общий system-prompt.md` сейчас до модели **не доходит**: это рабочая
копия пользователя. Прежняя инструкция «вставить раздел 9 в конец `общий system-prompt.md`»
сама по себе Visual Protocol в чат не включает — блок должен попасть в `system-prompt.md`
(вручную или через вкладку «System», которая пишет именно туда). Это не запрет и не поломка,
но без этого шага весь дальнейший проект бессмысленен.

## 4. Профиль, память и `memoryEnabled`

- `memoryEnabled = store.get("memory_enabled", false)` (`app.js:749`); переключение —
  кнопка `memory-btn` (`app.js:2233–2241`), состояние пишется в `localStorage`.
- `currentProfile = store.get("memory_profile", "core")` (`app.js:1807`); смена — только
  при закрытии окна профилей (`app.js:2287–2295`), затем `loadMemory()` (`2157–2170`).
- `GET /api/memory?profile=` (`history-server.py:1445–1459`) читает **весь файл**
  `memory\<profile>.md` (валидация имени `_memory_path`, `1420–1434`: латиница/цифры/`-`/`_`,
  обязательное пребывание внутри `memory\`).
- Профили в списке = `memory\*.md` (`1437–1443`).

**(Ф5) Память — это один выбранный файл целиком, а не инжект по ключевым словам.**
Ключевые слова в Strawberry используются в другом месте и вручную:
`POST /api/profile/route` (`1605–1662`) делает **отдельный** LLM-вызов по кнопке и пишет
`profiles\current.json` (якоря/родовые слова — фактическое содержимое прочитано: тема
«лесбиянки…»), а `POST /api/profile/build-from-current` (`1665+`) по этим якорям собирает
файл профиля из чатов. Автоматического подбора `memory\*.md` под каждое сообщение нет.

Следствие дляVisual Protocol: `memory\krea.md` и `memory\wangp.md` попадают в контекст
только когда выбран **этот** профиль и флаг включён. Они не «включаются на время картинок».
Поэтому правило приоритета адаптера над памятью (§9.2 п.5) остаётся нужным, а селектор
целевой генерации не должен строиться на переключении профилей.

## 5. Как в Strawberry хранятся пользовательские настройки

```
web/app.js:15
const store = {
  get(k, d) { localStorage.getItem("strata." + k) ... },
  set(k, v) { localStorage.setItem("strata." + k, JSON.stringify(v)) },
};
```

Занятые ключи (прочитаны в коде): `memory_enabled`, `memory_profile`, `sampling`,
`chat`, `apikey`, `reasoning_limit`, `currentHistoryId` (`app.js:1043`,
`history-module.js:93, 527`), `historyPinnedOnly`, `historyAiMode`, `historySortMode`,
`historyNextNumber` (`history-module.js:102–104, 352–398, 642–643`).
Подключения к LLM живут в **своём** ключе `strata.v1` (`connections.js:16, 72, 80`) —
состояние бэкенда изолировано от прочих настроек.

Серверного хранилища интерфейсных настроек нет: `saved_filters.json` — это фильтры
истории, сейчас `[]` (2 Б).

**(Ф6) Граница localStorage.** Выбор, сохранённый через `store`, живёт в браузере и
привязан к источнику (`127.0.0.1:порт`). Он переживает перезапуск Strawberry и закрытие
вкладки, но не переносится в другой браузер / на другой порт / в приватный режим. Для
настройки «целевой генератор» это приемлемо (так же хранится выбранный профиль памяти),
но это надо назвать прямо, а не обещать «сохраняется везде».

## 6. Жизненный цикл: новый чат, переключение чатов, перезапуск

- **Новый чат** — `app.js:1476–1484`: обнуляются только `messages` и `store.set("chat", …)`
  (плюс синхронизация истории, `history-module.js:29–41`). Настройки, флаг профиля, имя
  профиля и любой новый ключ `store` **не трогаются**.
- **Переключение чата** — `history-module.js` патчит `window.setMessages`
  (`history-module.js:19–27`, `app.js:2999–3002`) и пишет `currentHistoryId`
  (`history-module.js:527`). `systemPromptText` и `memoryText` при этом **не
  перезагружаются**: они глобальные и загружены один раз при старте (`app.js:2806–2807`).
- **Перезапуск страницы/сервера** — при старте заново читаются `store` (флаг, профиль,
 sampling), затем `loadMemory()` и `loadSystemPrompt()`.

Вывод: настройка, лежащая в отдельном ключе `store`, автоматически удовлетворяет
требованиям «не сбрасывается новым чатом», «не теряется при переключении чатов»,
«переживает перезапуск» — без какой-либо новой инфраструктуры.

## 8. Чего в Strawberry нет (границы решения)

- **Нет автозагрузки Markdown-скилов.** Ничего не сканирует папку на предмет инструкций;
  тексты берутся ровно из двух мест: `system-prompt.md` и один `memory\<profile>.md`.
- **Нет реестра «настроек генерации» на сервере.** Любая серверная новая сущность =
  новый эндпоинт + новый файл + новый код в `history-server.py`.
- **Есть статика `/web`.** `app.mount("/web", StaticFiles(directory=WEB_DIR))`
  (`history-server.py:2076`, шрифты — `2073`; сама страница — `2064–2070`). Значит файл
  вида `web\image-adapters.js` отдаётся браузеру **без единой строчки нового серверного
  кода**. Это и есть «более простой механизм, который уже есть в коде» (вариант В, §2
  плана интеграции).
- **Картинки в чат уже есть:** `MAX_IMAGES_PER_MESSAGE = 4` (`app.js:1157`),
  `visionEnabled()` (`app.js:1559`) — сценарий «правка изображения» в Strawberry
  физически поддерживается (изображение уходит в запрос, модель его видит).

## 10. Риски, найденные в коде (для раздела «риски» итогового отчёта)

1. **`memoryEnabled` выключает весь System Prompt** (Ф2). Если ничего не менять,
   Visual Protocol исчезает вместе с профилем → сценарий 10 не выполняется.
   Минимальное исправление — вынести общий промпт и адаптер из-под `if (memoryEnabled)`,
   оставив под флагом только `<memory>`. Это меняет текущее поведение (OFF сейчас = нет
   системного сообщения вообще), поэтому требует явного согласия пользователя.
2. **`system-prompt.md` пуст, а правится пользователем другой файл** (Ф4): блок можно
   вставить «не туда» и месяцами не видеть эффекта.
3. **`prefixMessages` = 1** (app.js:1393): любое добавление **второго** system-сообщения
   сломает и пометку префикса, и, у части бэкендов, приём запроса. Динамический адаптер
   обязан идти в то же первое system-сообщение.
4. **localStorage = браузер+источник** (Ф6): выбор не переносится между браузерами и
   портами; в приватном режиме `store.set` молча работает только в памяти (`app.js:17`).
5. **Память может противоречить адаптеру** (`memory\krea.md`, `memory\wangp.md` о
   зафиксированных cfg/шагах и seed). Порядок «промпт → память» и правило приоритета
   адаптера (§9.2 п.5) — штатная защита; менять файлы памяти не нужно.
